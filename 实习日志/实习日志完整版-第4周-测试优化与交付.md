## 第22天 — 2026年7月27日（星期一）— 系统级代码审查

**上午：**

最后一周，任务从"开发"转向"质量保障"。带教老师安排我做一次系统级的全量代码审查——不是只看自己的代码，而是审查整个项目的 192 个 Java 文件 + 65 个前端文件。

上午我花了 3 小时建立审查框架。我问后端组的前辈"怎么审查一个你不熟悉的模块"——他的建议是"四条线并行"：安全线（认证、授权、输入校验、密钥管理、日志安全）；性能线（N+1 查询、全表扫描、缓存策略、数据库索引）；数据线（表结构、约束、索引、迁移脚本）；代码质量线（异常处理、DTO 设计、命名规范、死代码）。

我按照这四条线，使用了 Claude Code 作为辅助工具，分四路并行扫描了项目。审查了整整一上午，标注出了初步问题清单。

**下午：**

下午我把标注的问题整理分类，并约了带教老师逐条确认。最终形成了 81 个问题的清单，按严重程度分为四个等级——CRITICAL（7个，必须在交付前修）、HIGH（24个，影响安全/性能）、MEDIUM（22个，影响可维护性）、LOW（28个，建议性改进）。

其中几个 CRITICAL 问题让我后背发凉——
1. `OperationLogAspect` 在记录操作日志时，将请求参数完整序列化到数据库的 `t_operation_log` 表中。这意味着"修改密码"接口的 `oldPassword` 和 `newPassword` 会以明文形式存入日志表——任何能查日志的人都能看到所有用户的密码变更记录
2. `AiChatController` 的 AI 聊天端点因为路径匹配 `/api/ai/**`，在 `SecurityConfig` 中被设为 `permitAll()`——任何人不需要登录就能读取任意用户的 AI 聊天历史
3. JWT 没有撤销机制——Token 签发后 24 小时内无法主动失效，如果 Token 被泄露（比如通过 WebSocket URL 被日志记录），攻击者有最多 24 小时的时间窗口

**学习方式：**
- 带教指导：后端组的前辈传授的"四条线"审查框架——结构化的审查比漫无目的地查看代码有效得多
- 行业著作：后端组的前辈推荐了《The Art of Software Security Assessment》——虽然只读了前两章，但对安全代码审查的思维方式有很大启发
- AI 辅助：使用 Claude Code 分四路并行扫描，每条线独立输出问题列表——比人工逐文件查看效率高得多
- 实践验证：对每个 CRITICAL 问题都在本地环境验证了"攻击能否成功"

**收获与思考：**
代码审查中最震撼的发现是——"看起来正常工作"的代码和"安全的代码"之间有很大的鸿沟。OperationLogAspect 的代码跑了一年没出过 Bug，但它把密码写入了日志，这比一个 Bug 更危险——因为没人知道它存在。

## 第23天 — 2026年7月28日（星期二）— 性能优化

**上午：**

今天集中火力修性能问题——代码审查中标注了 7 个 N+1 查询。

第一个也是影响最大的——`OrderServiceImpl.toVO()` 方法。每次把 Order 转换为 OrderVO 时，都会为每个订单单独执行两次数据库查询——`carTypeMapper.selectById(order.getCarTypeId())` 和 `driverMapper.selectById(order.getDriverId())`。如果一个用户有 20 个历史订单，查询订单列表就会产生 1（查订单）+ 20×2（逐条查车型和司机）= 41 次数据库查询。

我问后端组的前辈这种问题怎么修。他给出了标准的 N+1 修复三步法——1. 收集所有 ID → 2. 用 `selectBatchIds` 批量查询 → 3. 用 Map 查找。我把 `toVO()` 改成 `toVOList()`——先收集所有 `carTypeIds` 和 `driverIds`，一次性批量查询，构造 Map<Long, CarType> 和 Map<Long, Driver>，然后遍历订单时从 Map 中取。查询次数从 1+2N 降为 3（查订单 + 查所有车型 + 查所有司机）。

同样的方法修复了 `CouponServiceImpl.listUserCoupons()` 和 `PaymentServiceImpl.listByUser()` 中的 N+1 查询。

**下午：**

下午继续修数据层性能问题。`OrderServiceImpl.review()` 在计算司机平均评分时，把该司机所有评价加载到 Java 内存中计算平均值——用 `SELECT COALESCE(AVG(rating), 0) FROM t_review WHERE driver_id = ?` 替代。`getTodayRevenue()` 同样改为 `SELECT COALESCE(SUM(final_price), 0)`。

`AiChatServiceImpl.buildChatParams()` 也有问题——每次对话从数据库加载全部历史消息（`selectList` 无 LIMIT），但实际只使用最近的 20 条。我改为 `orderByDesc(createTime).last("LIMIT 21")` + 反转列表。这样无论会话有多长，数据库只返回 21 行。

**学习方式：**
- 带教指导：后端组的前辈教的 N+1 三步修复法——"收集 → 批量 → 映射"，三个步骤拆解清晰
- 动手比较：在 IDEA 的 Database 工具中执行原始 SQL 和优化后的 SQL，对比 `EXPLAIN` 结果和执行时间
- B 站视频：看了"美团技术博客"的"MySQL 索引优化实战"——理解了覆盖索引、回表查询、最左前缀原则
- AI 辅助：Claude Code 帮助我逐行检查了修改后代码的编译和逻辑正确性

**收获与思考：**
N+1 问题是 ORM 框架最常见也最容易被忽视的性能陷阱——单独一次查询很快（2ms），但放在 1000 次循环里就是 2 秒。性能问题有"温水煮青蛙"的特点——数据量小的时候感受不到，数据量一上来系统就崩了。

## 第24天 — 2026年7月29日（星期三）— E2E 全量测试

**上午：**

今天运行项目的 E2E 测试套件。测试套件由 20 个 `.mjs` 脚本组成，共计 91 个测试用例，分为四个分组——核心链路回归（认证、订单、司机、支付、综合 API）、业务模块专项（退款、通知、地址、优惠券、VIP、班线）、安全边界（IDOR、JWT 安全、支付安全、输入安全）、并发风控（并发抢单、风控规则、WebSocket）。

测试直接通过 Node.js 的 `fetch()` API 调用 `http://localhost:8080` 的后端接口，不需要启动前端。我按照测试脚本的要求先启动了 Spring Boot 服务（`mvn spring-boot:run`），然后在 `tests/` 目录下执行 `node test-suite.mjs`。

**遇到的问题：**
第一次运行测试套件到后半段时大量脚本连续失败——错误信息显示登录接口返回 `{"code":9002, "message":"请求过于频繁，请稍后重试"}`。原因是全局限流拦截器（`RateLimitInterceptor`，每分钟限制 60 次请求/IP）被触发。前四个脚本（约 42 个请求）通过后，第五个脚本（36 个请求）的后半段全部被限流拒绝，导致后续所有以登录开始的脚本全都级联失败。

**下午：**

跟后端组的前辈讨论了这个问题的本质——在开发环境，"自我保护机制"（限流、验证码频率控制）反而成为测试的阻碍。解决办法有几个——第一种是修改 `application.yml` 为测试环境关闭限流，但这样测不到限流逻辑；第二种是测试脚本之间共享登录 Token，避免重复登录。

我选了"组合方案"——修改测试编排器 `test-suite.mjs`，在每篇测试脚本执行前用 `redis-cli KEYS "rate:*"` 查找并清除 Redis 的限流计数器，确保每篇脚本从零开始计数。同时把测试脚本间的间隔时间从 3 秒缩短为 2 秒（有了 Redis 清理后不需要长时间等待限流窗口过期）。

修改后重新跑了全量测试，核心链路回归 42/42 = 100% 通过（认证 12/12、订单 6/6、司机 8/8、支付 6/6、输入安全 8/8、并发 2/2）。业务模块专项和安全边界的部分脚本因为测试账户数据问题未能完全通过，但核心功能链条是完整的。

**学习方式：**
- 带教指导：后端组的前辈关于"测试环境的限流处理"——生产环境和测试环境的安全策略应该分开
- 动手调试：用 `redis-cli MONITOR` 监控 Redis 的实时命令，发现了限流计数器的 Key 规律
- AI 辅助：Claude Code 帮助分析了 91 个测试用例的结果，分类了真实失败和级联失败
- 问题复盘：和后端组的前辈一起讨论了"为什么测试环境中限流会级联失败"——核心是"无状态的测试设计"（每个脚本独立登录）与"有状态的限流器"（按 IP 累计）之间的冲突

**收获与思考：**
测试不仅是"验证功能能用"，更是"验证系统在异常情况下不会崩溃"。今天学到了两件事——一是限流器需要为测试环境提供白名单机制，二是测试脚本之间的状态隔离很重要。

## 第25天 — 2026年7月30日（星期四）— Docker 部署 + 生产环境

**上午：**

今天开始做部署方案。项目需要支持 Docker Compose 一键启动，带教老师说目标是"新同事入职 10 分钟把项目跑起来"。

上午我阅读了公司内部每个项目使用的标准部署模板——包含后端 Dockerfile、前端 Dockerfile、前端 nginx.conf、docker-compose.yml、.env 环境变量文件、build.ps1 构建脚本。

后端 Dockerfile 基于 `eclipse-temurin:17-jre`（比标准 OpenJDK 镜像约小 40%），将 `mvn package` 产出的 JAR 复制到容器中，用 `java -jar app.jar` 启动。前端 Dockerfile 基于 `nginx:alpine`（约 5MB），将 `npm run build` 产出的 dist 复制到 nginx 的 `/usr/share/nginx/html` 目录。

**下午：**

下午编写了 nginx.conf 和 docker-compose.yml。

nginx.conf 配置了三个关键项——Gzip 压缩（`gzip_types text/css application/javascript` 等文本资源）、SPA 路由回退（`try_files $uri $uri/ /index.html` 处理 Vue Router 的 history 模式）、API 反向代理（`proxy_pass http://backend:8080`——容器间通过服务名互相访问）、WebSocket 代理（`proxy_http_version 1.1; proxy_set_header Upgrade $http_upgrade; Connection "upgrade"`）。

`docker-compose.yml` 编排了四个服务——MySQL 8.0（挂载 `init.sql` 到 `/docker-entrypoint-initdb.d/`，启动时自动初始化数据库；健康检查 `mysqladmin ping` 间隔 10s）、Redis 7 Alpine（健康检查 `redis-cli ping`）、Spring Boot 后端（依赖 MySQL 和 Redis 健康通过后才启动，环境变量注入数据库和 Redis 连接信息）、Nginx 前端（依赖后端启动，对外暴露 80 端口）。

另外，我还配置了生产环境的 `application-prod.yml`——MySQL SSL 强制启用、MyBatis SQL 日志关闭、Swagger 文档关闭、敏感配置全部通过环境变量无回退值注入。

**学习方式：**

- 官方文档：Docker Compose Specification（compose-spec.io）——`depends_on` 的 `condition: service_healthy` 语法是 compose v3.9 才支持的
- B 站视频："尚硅谷 Docker 实战教程"——看完 Docker Compose 章节（约 2h）
- 带教指导：运维组的同事帮我检查了 nginx.conf 的 WebSocket 代理配置

**收获与思考：**
Docker 的"一次构建，到处运行"让部署变得标准化。今天理解了——部署不只是"把代码放到服务器上"，还包括环境变量管理、健康检查、依赖启动顺序、数据持久化、网络隔离等多个维度。

## 第26天 — 2026年7月31日（星期五）— 安全性全面加固

**上午：**

今天进行最后一轮安全性加固。周二代码审查中发现的 7 个 CRITICAL 问题必须全部修复。

1. **明文密码日志**：在 `OperationLogAspect.getRequestParams()` 中添加敏感参数过滤——参数名包含 "password" / "secret" / "token" / "key" 的，序列化时替换为 `"***"`。同时 `UserController.changePassword()` 的 `@LogOperation` 增加 `saveRequestParams = false` 双重保护。

2. **AI 聊天未认证**：从 `SecurityConfig` 中移除 `/api/ai/**` 的 `permitAll()`，改为要求登录。`AiChatController.getSessionMessages()` 增加 `Authentication` 参数和 userId 校验——只能看自己的聊天记录。

3. **JWT 无撤销机制**：新增 `TokenBlacklistService`，使用 Redis `SETEX` 以 Token 过期时间为 TTL 存储黑名单。`JwtAuthFilter` 在验证 JWT 后额外检查黑名单。登出和改密时自动将 Token 加入黑名单。

**下午：**

4. **密钥外部化**：应用配置文件中之前硬编码了 JWT Secret、DeepSeek API Key、高德地图 Key。修改为 `${ENV_VAR:default}` 占位符格式，生产环境通过环境变量注入且无回退值。

5. **CORS 收紧**：从 `*` 通配符改为只允许 `localhost` 的端口范围，关闭 `allow-credentials`（因为使用的是 JWT Bearer Token，不是 Cookie 认证）。

6. **WebSocket Token 泄露**：Token 从 URL Query Param 改为 Cookie 传递（已在第 15 天修复）。

7. **验证码安全**：`Math.random()` 替换为 `SecureRandom`（`Math.random()` 的 LCG 算法可被预测）。

8. **登录暴力破解**：新增 Redis 计数机制，同一手机号/用户名 5 次失败后锁定 15 分钟。

9. **CSRF 禁用说明**：在 `SecurityConfig` 中增加注释，说明 CSRF 禁用原因（纯 REST API + JWT 无状态架构），并注明"若未来改用 Cookie 存储 JWT，需重新启用 CSRF 保护"。

**学习方式：**
- 带教指导：带教老师逐条检查了每个安全修复的效果——"安全修复不能大概对，必须精确对"
- 安全标准：参考了 OWASP Top 10 (2021)，对照检查了项目是否覆盖了常见 Web 安全风险
- AI 辅助：Claude Code 帮助验证了每个安全修复的正确性和边界条件
- 知识巩固：对照两周前在学校学的"信息安全"课程，把理论（加密算法、认证协议、访问控制）和实际（JWT、BCrypt、RBAC）联系起来

**收获与思考：**
安全不是"一次性修完"的——它是持续的、迭代的。今天修了 7 个 CRITICAL + 19 个 HIGH 问题，不代表以后就没有新问题了。关键是把"安全思维"融入到日常编码中——写每个接口都问自己"如果我是攻击者，我会怎么利用这个接口？"

## 第27天 — 2026年8月1日（星期六）— 全量问题修复与文档完善

**上午：**

今天是实习最后一个周六，但工作强度不小。上午进行了"终极修复"——处理代码审查中剩余的 25 个 MEDIUM/LOW 问题。

关键改动——
- 创建 `BusLineSaveRequest` DTO 替代 `BusLine` Entity 作为请求体——防止客户端传入不可控字段（Mass Assignment 攻击）

# 实习后持续迭代（2026.07.03 更新）

实习结束后，我继续对项目的调度系统进行了六轮工程增强（v1.0 → v1.5），将"功能可运行"的 MVP 升级为"可展示工程深度"的系统设计作品。

## 迭代动机

实习期间完成了 97 个 API、28 张表、41 个页面的全栈功能开发，但调度模块（订单如何派给司机）在实习期间是简化实现的——基本逻辑是"找最近的在线司机"，没有深入处理并发冲突、调度公平性、系统收敛性等分布式系统工程问题。

实习结束后，我给自己定了一个目标：**把调度系统做成可以用来面试讲解的深度**。

## 六轮迭代

| 版本 | 日期 | 核心增量 | 关键设计决策 |
|------|------|---------|------------|
| v1.0 | 7月初 | 形式化订单状态机 | 将散落的 if-else 状态管理重构为 OrderStatus 枚举 + ALLOWED_TRANSITIONS Map。流转规则集中在一张表里，新增状态只改一个文件。18 个单元测试覆盖全部合法/非法路径 |

## 核心技术成果

### 1. 并发调度一致性保障
- **方案**：二阶分布式锁（Redis Redisson）
- **流程**：lock("order:dispatch:{id}") → tryLock("driver:lock:{id}", 500ms) → 失败 fallback
- **保障**：锁顺序 100% 统一 → 数学上无死锁；加锁后重读 DB → 防 ABA 竞态
- **验证**：100 订单 × 20 司机压测，零重复分配、零订单丢失

### 2. 可收敛的动态评分引擎
- **静态层**：距离 40% + 评分 30% + 空闲 20% + 拒单惩罚 10%
- **动态层**：接单 +5 分、拒单 -10 分、10min 半衰期衰减、上下限(-30, +20)
- **效果**：5 轮派单后成功率 ↑ 20pp（50% → 70%），评分波动 ↓ 50%

### 3. 事件溯源审计追踪
- `t_order_event` 表覆盖 12 种事件类型（DRIVER_ASSIGNED/REJECTED/BUSY/RELEASED 等）
- 一条 SQL 回溯任意订单完整生命周期
- 为未来 Kafka 异步消费和 CQRS 架构铺路

### 4. 三层可观测性体系
- **Metrics**（数据）：成功率、平均延迟、司机负载分布
- **Health**（评分）：加权公式 S/A/B/C/D 五级
- **Anomaly**（检测）：连续拒单≥5、失败≥3、锁竞争≥10 自动标记

### 5. AI 辅助开发实践
- **工具**：Claude Code CLI + Agent 体系 + 5 个 MCP 工具
- **分工**：AI 执行 60%（样板代码、测试脚本、文档生成），人类决策 40%（架构、并发、评分设计）
- **约束**：建立 20 条规则（CLAUDE.md）约束 AI 行为
- **效率**：代码生成 2.5×、测试编写 2×、文档生成 50×
