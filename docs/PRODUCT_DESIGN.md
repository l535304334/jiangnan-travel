## 一、产品定位

### 1.1 产品口号
**"行遍江西，智享出行"** — 以江西地域文化为灵魂、以智慧出行为核心的一站式出行平台。

### 1.2 产品类型
- **主赛道**：城市出行 + 城际出行（双引擎）
- **差异化**：江西省首个"出行+文旅"深度融合的智慧平台
- **商业模式**：乘客付费 + 司机抽佣 + VIP会员 + 城市合作推广

### 1.3 竞品对标
| 维度 | 滴滴出行 | 高德打车 | 江南出行 |
|---|---|---|---|
| 城市覆盖 | 全国 | 全国 | 江西11城 |
| 文旅整合 | 无 | 无 | 核心特色 |
| AI能力 | 基础 | 基础 | DeepSeek深度集成 |
| 价格透明度 | 中 | 高 | 极高（阶梯计价明细） |
| 文化认同 | 无 | 无 | 强（墨色江南设计语言） |

### 1.4 核心价值主张
1. **透明计价** — 四段阶梯计价，每公里单价清清楚楚
2. **智慧出行** — AI预测需求热点、智能派单
3. **文旅融合** — 司乘对话中融入江西风土人情，行程间隙展示城市故事
4. **安全可靠** — 风控引擎 + 一键报警 + 行程分享 + 隐私保护

## 三、业务流程总览

### 3.1 核心业务闭环
```
用户下单 → 系统计价 → 智能派单 → 司机接单 → 行程导航 → 完成支付 → 双向评价
    ↑                                                                   ↓
    └──────────────── 数据沉淀 → AI优化 ─────────────────────────────────┘
```

### 3.2 订单状态机（7状态）
```
[0]待接单 → [1]已接单 → [2]已到达 → [3]行程中 → [4]已完成
                    ↓                ↓
               [5]已取消         [6]风控拦截
```
- 状态0→5：用户取消（仅待接单状态可取消）
- 状态1→5：司机拒绝（仅已接单状态）
- 状态0→6：风控引擎自动拦截

### 3.3 计价流程（短途/长途双引擎）
```
输入起终点 → 高德路线规划 → 判断距离
  ├─ ≤50km → 短途模式 → 三款车型选择 → 阶梯计价（4段）
  └─ >50km → 长途模式 → 两款车型选择 → 长途阶梯计价（4段半价）
```

### 3.4 优惠券流转
```
管理员创建活动 → 发放优惠券 → 用户从活动页领取 → 下单时选择使用 → 完成核销
```

### 3.5 AI助手交互流程
```
用户提问 → 构建系统提示词（含地标+寄语） → 加载历史对话 → DeepSeek API → SSE流式返回
```

## 四、功能缺失分析

### 4.1 已发现的功能缺失（按优先级）

#### P0 — 阻塞性缺失
| 编号 | 缺失功能 | 影响 | 建议 |
|---|---|---|---|
| F-01 | 无消息通知系统 | 司机无法接收派单通知、用户收不到行程变更 | 新增 t_notification 表 + WebSocket推送 |
| F-02 | 优惠券无使用入口 | 下单时无法选择优惠券 | 下单页增加优惠券选择弹窗 |
| F-03 | 司机端数据均为假数据 | 司机首页/收入页/个人页全是硬编码 | 对接到后端真实API |
| F-04 | 下单页地址搜索仅限预置20个地标 | 无法搜索真实地址 | 接入高德POI搜索API |

#### P1 — 严重缺失
| 编号 | 缺失功能 | 影响 | 建议 |
|---|---|---|---|
| F-05 | 无活动页 | 优惠券只能从优惠券页面直接领，无运营感 | 新增活动页+活动表 |
| F-06 | 无VIP会员体系 | 缺少用户留存手段 | 新增VIP等级表+会员中心 |
| F-07 | 无数据可视化 | 管理后台缺乏图表分析 | 集成ECharts |
| F-08 | 行程追踪页WebSocket未连接 | 无法看到司机实时位置 | 实现WebSocket对接 |
| F-09 | 无支付集成 | 支付按钮是模拟的 | 集成微信/支付宝SDK |

#### P2 — 一般缺失
| 编号 | 缺失功能 | 影响 | 建议 |
|---|---|---|---|
| F-10 | 无发票开具功能 | 商务用户无法报销 | 实现电子发票API |
| F-11 | 无语音输入 | 银发族使用困难 | 集成Web Speech API |
| F-12 | 班线系统未开发 | t_schedule_route/order表空置 | 开发城际班线功能 |

### 4.2 功能重复/冲突
| 问题 | 说明 |
|---|---|
| 登录页面包含三角色登录 | Login.vue包含用户+司机+管理员登录，但又有独立DriverLogin.vue和AdminLogin.vue。建议保留Login.vue作为唯一入口 |

## 五、权限设计问题

### 5.1 当前权限模型
- 使用3个独立JWT token（token/driverToken/adminToken），零角色设计
- SecurityContext仅设置userId，无角色信息
- Controller层通过Authentication获取userId后手动查表

### 5.2 问题
1. **三套token体系不统一** — 无法区分用户和司机在同一设备上的行为
2. **角色鉴权缺失** — 任何持有效token的人可以调用任意端点
3. **司机和管理员API无角色保护** — 可能导致越权

### 5.3 建议
```
JWT payload 增加 role 字段：
{ sub: userId, phone: "13900001111", role: "USER|DRIVER|ADMIN" }
SecurityConfig 增加角色鉴权：
.requestMatchers("/api/admin/**").hasRole("ADMIN")
.requestMatchers("/api/driver/**").hasRole("DRIVER")
```
