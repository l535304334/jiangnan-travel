# 面试问答库

> 每个问题提供标准回答。面试时不必逐字背诵，但关键数据和设计理由必须准确。

## Q1：你这个项目最难的地方是什么？

**标准回答**：

最难的是并发调度的一致性保证。

具体场景：50个乘客同时下单、20个司机在线。系统要在几百毫秒内给每个订单找到最合适的司机，而且必须保证**一个司机不会被两个订单同时分配**——这在分布式环境下不是一把 synchronized 能解决的。

我的方案是二阶分布式锁。第一层锁订单保证不重复派，第二层 tryLock 司机——500 毫秒超时，拿到就分配，拿不到自动 fallback 下一位。

关键细节是锁顺序必须 100% 统一——永远先 order 锁再 driver 锁。这是死锁预防的经典条件：不存在 A 等 B、B 等 A 的循环等待。另外加锁后必须重读数据库——因为在你获取锁的间隙里，司机状态可能已经被其他线程改了。这个 ABA 问题是我在压测中真实遇到的，修复后就没再出现过。

100 订单 × 20 司机压测验证：零重复分配、零死锁。

## Q2：为什么这样设计数据库？

**标准回答**：

数据库设计我遵循了三条原则。

第一，**一表一职责**。t_order 管订单，t_payment 管支付，t_driver 管司机，t_review 管评价——每张表只做一件事。不搞大宽表，避免更新异常。

第二，**事件与状态分离**。订单的当前状态存在 t_order.status 里，但状态的变化过程存在 t_order_event 里。这是一个轻量级的事件溯源设计。好处是：任何时候查一个订单经历了什么，一条 SELECT * FROM t_order_event WHERE order_id=X ORDER BY event_time 就能回溯全流程。不需要在订单表里加 20 个时间戳字段。

第三，**迁移脚本版本化管理**。init.sql 是建表脚本，migration_v1.1、v1.2、migration_optimize、migration_state_machine 是按版本的增量变更。这在团队协作中是标准实践——不会出现"你的数据库和我的不一样"。

27 张表覆盖了用户体系、订单体系、支付体系、司机体系、营销体系、AI 体系、风控体系和消息体系。

## Q3：调度逻辑怎么实现的？

**标准回答**：

调度逻辑分三步。

**第一步，触发**。订单支付成功后状态变为 PAID，系统自动触发调度——不是司机抢单模式，是平台派单模式，可以基于全局信息做最优匹配。

**第二步，评分排序**。把所有在线空闲司机按评分引擎排序。评分引擎有四个维度：距离占 40%——越近越好；司机评分占 30%；空闲时间占 20%——空闲越久越优先；拒单惩罚占 10%——拒单多的排名下降。在这之上还有一个动态学习层：司机每次接单加分、拒单扣分，分数有 10 分钟半衰期自动衰减。

**第三步，并发分配**。按排序结果从上往下尝试：先锁订单，再 tryLock 司机。拿到锁就分配，拿不到就跳下一个。所有候选都失败就记录失败事件然后告警。

这三个步骤保证了：正确性（不会重复分配）、公平性（不会被少数司机垄断）、可收敛（系统自己稳定）。

## Q4：有没有用到 AI 辅助开发？怎么用的？

**标准回答**：

用了。全程使用 Claude Code 辅助开发。

但不是"AI 帮我写了所有代码"——AI 参与度大约 60%，主要在做机械性工作：样板代码生成、测试脚本编写、文档格式化。剩下 40% 的关键决策都是我自己做的——锁的设计、状态机的设计、评分收敛机制。

我建立了 20 条规则来约束 AI 的行为。比如"不自动修改系统环境配置"、"删除文件前必须确认无引用"、"同一问题出现三次才允许新增规则"。这些规则让我和 AI 的协作更可控。

效率提升：代码生成快 2.5 倍，测试编写快 2 倍，文档生成快 50 倍。但最有价值的不是速度——是 AI 让我能专注于架构设计和并发安全这些需要深度思考的问题。

核心经验是：AI 是放大器，不是替代品。关键逻辑——特别是并发控制——不能全交给 AI。我在压测中发现了一个 ABA 竞态 bug，就是 AI 生成的初版代码遗漏了加锁后重读数据库这个细节。这正好验证了"人类主导 + AI 增强"模式的必要性。

## Q5：如果重做你会优化什么？

**标准回答**：

三个方向。

**第一，评分引擎的实时化**。当前 findCandidates 每次都 SELECT * FROM t_driver WHERE status=1 全表扫描。司机数量到万级别这会成为瓶颈。如果重做，我会用 Redis Sorted Set 实时维护在线司机排名——O(logN) 查询而不是 O(N) 扫描。

**第二，事件系统的异步化**。当前 order_event 是同步写入的，每次状态变更都伴随着一次 INSERT。如果重做，事件写入可以改成异步——先发到 Kafka，下游消费者负责持久化和统计。这样调度延迟不会受事件写入影响。

**第三，评分引擎接入真实数据**。当前评分收敛的验证依赖模拟压测数据。如果接入真实运营数据，可以做更精细的 A/B 测试——比如对比"有衰减"和"无衰减"两组司机的长期接单率差异。

**但当前架构不需要大改**——这三个优化都是增量式的，因为 ScoringEngine 是接口、事件系统是独立表、锁机制不依赖评分实现。

## Q6：如何保证系统可扩展？

**标准回答**：

可扩展性我分三层考虑。

**代码层面**：ScoringEngine 是接口，替换评分策略只需要实现新类 + 改一行注入。新增订单状态只需枚举中加 1 行 + 流转表加 1 个 entry。这是开闭原则——对扩展开放、对修改关闭。

**架构层面**：事件系统（order_event）为异步化铺了路。未来把事件接入 Kafka，下游消费者可以做实时统计、风控告警、数据仓库——不需要改业务代码。

**部署层面**：Spring Boot 应用是无状态的，加实例 + Nginx 负载均衡即可水平扩展。当前的瓶颈在 MySQL 写和 Redis 单点——如果上生产，MySQL 可以做读写分离，Redis 可以用 Cluster 模式。

还有一点：状态机是形式化的，不是散落 if-else——这意味着新来的开发者可以快速理解系统行为，不需要读遍所有 Service 代码。

## Q7：为什么选择 Spring Boot + MyBatis-Plus 而不是其他框架？

**标准回答**：

选型主要考虑三点。

Spring Boot 是 Java 生态的企业级标准，依赖注入、自动配置、AOP、事务管理都是开箱即用。对于需要事务一致性的订单和支付系统来说，Spring 的声明式事务是刚需。

MyBatis-Plus 比 JPA 更灵活。出行系统的查询场景很复杂——按状态筛选、按时间范围、按地理位置排序。MyBatis-Plus 的 Lambda 条件构造器比 JPA 的 Criteria API 更直观，而且支持原生 SQL 落盘——复杂查询不会被 ORM 限制。

Redis Redisson 的选择很关键。Redisson 不是简单的 Redis 客户端——它提供了分布式锁、公平锁、读写锁这些高级原语。我的二阶锁方案如果换成 Jedis + 手写 Lua 脚本，代码量和出错概率会大很多。

总的来说，这不是"哪个框架流行就用哪个"——每个选型都有明确的工程理由。

## Q8：这个项目最大的收获是什么？

**标准回答**：

三个收获。

**技术上**，真正理解了分布式锁的语义。不是"用了 Redisson"就完了——锁顺序为什么重要、tryLock 和 lock 的区别、ABA 问题怎么发生怎么防、死锁的必要条件——这些东西看书和实际写代码是完全不同的体验。

**工程上**，学会了"先设计再编码"。状态机的形式化、事件的溯源设计、评分的收敛分析——这些都不是写代码写出来的，是坐下来画图、列表、算复杂度得出的。如果一上来就写代码，大概率会写成 if-else 地狱。

**方法上**，验证了 AI 辅助开发的正确姿势。不是让 AI 替你做决定，是让 AI 帮你做执行层的工作——你负责判断和决策。这个分工很关键。而且建立规则约束 AI 的行为，比每次口头纠正高效得多。
