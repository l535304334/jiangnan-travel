# AI 辅助开发实践记录 (Vibe Coding Log)

> 定位：研究生复试"AI + 软件工程"话题的加分素材
> 核心理念：**人类主导 + AI 增强开发能力**

---

## 一、本项目中如何使用 AI

### 1.1 使用的 AI 工具

| 工具 | 用途 | 使用频率 |
|------|------|---------|
| **Claude Code (CLI)** | 主开发工具：代码生成、修改、测试、架构设计、文档 | 全程 |
| **Claude Agent 体系** | 代码审查、安全审查、构建修复、E2E 测试 | 按需触发 |
| **MCP 工具链** | MySQL 查询验证、Git 操作、Playwright E2E、文件操作 | 开发中高频 |
| **DeepSeek API** | 项目内的 AI 客服和出行推荐（业务功能，非开发工具） | 业务层 |

### 1.2 AI 参与的具体环节

```
需求分析 ──→ 架构设计 ──→ 编码实现 ──→ 代码审查 ──→ 测试 ──→ 文档
   🟡           🟡           🟢          🟢        🟢      🟢
 (人主导)     (人主导)     (AI增强)    (AI主导)  (AI主导) (AI主导)
```

| 环节 | AI 参与度 | 说明 |
|------|----------|------|
| **需求分析** | 20% | 人类定义问题和边界，AI 辅助拆解 |
| **架构设计** | 30% | 人类做关键决策（状态机、二阶锁、评分收敛），AI 辅助细化 |
| **编码实现** | 70% | AI 生成代码框架，人类审查和修正关键逻辑 |
| **代码审查** | 90% | AI 自动审查变更、检测安全/性能/风格问题 |
| **测试** | 80% | AI 生成单元测试和 E2E 测试脚本 |
| **文档生成** | 80% | AI 根据代码和设计生成结构化文档 |

### 1.3 人类主导的关键决策

以下决策由人类做出，AI 未参与：

1. **二阶分布式锁的锁顺序设计**（order → driver，防止死锁）
2. **状态机形式化方式**（枚举 + Map 流转表）
3. **评分收敛机制**（惩罚 + 衰减 + 上下限）
4. **事件溯源设计**（order_event 覆盖所有变更）
5. **三层可观测性体系**（Metrics / Health / Anomaly）

这些决策涉及对并发、分布式系统、系统稳定性等核心计算机科学概念的理解——AI 可以提供信息，但不能替代判断。

## 二、任务拆解方式

### 2.1 拆解策略

本项目采用**增量迭代**策略，每个版本聚焦一个核心问题：

```
v1.0: 基础状态机 → 先让订单状态正确流转
v1.1: 业务闭环   → 加入派单、计费、评价
v1.2: 并发调度   → 加入二阶锁、评分引擎
v1.3: 动态学习   → 加入反馈学习、指标统计
v1.4: 收敛验证   → 极端压测、异常检测、健康评分
v1.5: 工程整理   → 文档、面试表达、系统设计说明
```

### 2.2 拆解原则

1. **每版本只解决一个核心问题**：不在 v1.1 做并发优化，不在 v1.2 做评分收敛
2. **每版本必须可运行**：不积压未测试的代码
3. **每个版本有明确的验证标准**：v1.2 验证"零重复分配"，v1.3 验证"评分收敛"

## 三、AI 参与开发的方式

### 3.1 代码生成

**模式**：人类描述需求 → AI 生成初版代码 → 人类审查关键逻辑 → AI 迭代修复

**典型案例**：
- 状态机枚举：人类定义状态列表和合法流转，AI 生成枚举代码
- 二阶锁实现：人类描述锁顺序和 fallback 逻辑，AI 生成代码框架，人类审查锁释放时机

### 3.2 代码修改

**模式**：外科手术式修改 —— 不改无关代码，只改目标方法。

AI 的表现：
- ✅ **擅长**：添加导入、注入依赖、替换硬编码为枚举、添加方法调用
- ⚠️ **需要监督**：事务边界、锁释放时机（容易遗漏 finally 块）
- ❌ **不能信任**：并发安全逻辑（需要人类审查）

### 3.3 调试

**模式**：编译错误 → AI 自动修复 → 人类审查修复逻辑

本项目中的典型 bug 修复：
- **ABA 问题**：加锁后未重读 DB → 人类发现 → AI 辅助修复
- **Long/int 类型转换**：编译错误 → AI 自动修复
- **接口方法未实现**：WeightedScoringEngine 缺少 recordAccept 实现 → AI 补全空实现

### 3.4 测试生成

AI 自动生成：
- 18 个状态机单元测试（覆盖所有合法/非法流转路径）
- 50 订单并发压测脚本
- 100 订单极端压测 + 收敛分析脚本

人类负责：定义测试场景（哪些路径该通过、哪些该拒绝）

## 四、人机协作比例

| 维度 | 人工智能 | AI |
|--------|--------|-----|
| **架构决策** | 100% | 0% |
| **核心并发逻辑** | 60%（设计 + 审查） | 40%（代码生成） |
| **业务 CRUD** | 10%（审查） | 90%（生成） |
| **测试代码** | 20%（场景定义） | 80%（脚本生成） |
| **文档** | 30%（内容决策） | 70%（格式化 + 扩展） |
| **项目整体** | **~40%** | **~60%** |

> 关键区别：AI 做的 60% 是**可以被自动化的重复性工作**（样板代码、测试脚本、文档格式）。人做的 40% 是**需要判断力和领域知识的工作**（架构决策、并发安全、设计权衡）。

## 五、Bug 处理流程

### 5.1 处理流程

```
发现异常 → 复现 (AI辅助生成复现脚本)
         → 定位根因 (人类分析 + AI辅助搜索相关代码)
         → 修复 (AI生成修复代码)
         → 验证 (AI运行测试)
         → 回归 (AI运行全部测试)
```

### 5.2 典型案例：ABA 竞态条件

**现象**：并发压测中偶现司机被重复分配

**定位**：人类分析发现加锁后未重读 DB → 被锁保护的临界区中读到了过期状态

**修复**：在 tryLock 成功后加入 `driverMapper.selectById()` 重新读取司机状态

**教训**：分布式锁不是银弹 —— 锁只保证互斥，不保证数据新鲜度。AI 生成的初版代码遗漏了这个细节，说明并发安全逻辑不能完全交给 AI。

## 六、开发效率提升

| 指标 | 传统开发（估算） | AI 辅助开发（实际） | 提升 |
|------|---------------|-------------------|------|
| 代码生成速度 | ~200 行/天 | ~500 行/天 | 2.5× |
| 测试编写 | ~10 用例/天 | ~20 用例/天 | 2× |
| 文档生成 | ~2 天/文档 | ~20 分钟/文档 | ~50× |
| Bug 修复（编译错误） | ~10 分钟/个 | ~1 分钟/个 | 10× |
| Bug 修复（逻辑错误） | ~30 分钟/个 | ~20 分钟/个 | 1.5× |

**关键发现**：AI 对**机械性工作**（样板代码、格式化、测试数据准备）提速显著（10-50×），但对**需要深层理解的逻辑错误**提速有限（1.5×）。这验证了"人类主导 + AI 增强"模式的合理性。

## 七、遇到的问题与优化

### 问题 1：AI 生成的代码质量不稳定

**表现**：同一需求描述，不同轮次生成的代码质量差异大

**解决**：
- 先让 AI 输出设计方案，人类确认后再生成代码
- 对关键逻辑（并发、事务、锁）进行人工审查
- 建立 18 个规则约束 AI 行为（CLAUDE.md）

### 问题 2：过度设计倾向

**表现**：AI 倾向于生成"看起来更完善"但实际不必要的代码（工厂模式、多层抽象）

**解决**：
- 建立 Ponytail 规则（"不需要的代码就别写"）
- 每次新增功能前先问"是否已有现成方案？是否标准库已有？"
- Rule 19：规则膨胀抑制 —— 同一问题出现 ≥3 次才允许新增规则

### 问题 3：上下文漂移

**表现**：长会话中 AI 逐渐"忘记"项目的具体约束

**解决**：
- Rule 17：会话超过 15 轮触发主动上下文压缩
- 定期输出检查点（做了什么 + 改了什么 + 状态）
- 项目记忆系统：关键决策写入 memory

### 问题 4：需要约束 AI 不自动修改环境

**表现**：AI 在调试中可能自动修改 npm config、PATH 等系统配置

**解决**：
- Rule 14：环境维护原则 —— 不自动修改系统配置
- Rule 15：开发环境原则 —— 不自动升级依赖

## 九、总结

本项目是"**人类主导 + AI 增强**"开发模式的一次完整实践。核心经验：

1. **AI 是放大器，不是替代品**：它能让你快 2-10 倍，但不能替代你对并发、分布式、状态机的理解
2. **约束比自由更重要**：CLAUDE.md 的 20 条规则是保证 AI 行为可预测的关键
3. **关键决策永远是人做**：架构设计、并发安全、设计权衡——这些需要 CS 功底
4. **增量迭代优于大爆炸**：v1.0 → v1.5 的版本演进比一次性实现稳定得多
