## 二、核心系统设计解释（面试级表达）

### 2.1 为什么采用状态机而不是 if-else

**问题**：典型的电商/出行系统有 7-10 个订单状态，合法流转路径约 15 条。用 if-else 会产生什么？

```java
// 反模式：散落在各处的魔法数字
if (order.getStatus() == 0 && ...) { order.setStatus(1); }  // 哪个方法是合法的？
if (order.getStatus() == 3) { order.setStatus(4); }         // 能取消吗？不知道。
```

两个致命缺陷：
1. **流转规则不可见**：你看任何一个方法的代码，都无法知道完整的合法流转是什么。排查 bug 需要全局搜索所有 `setStatus` 调用。
2. **流转规则不可测试**：你无法单独验证"从 CREATED 能否跳到 COMPLETED"，只能通过集成测试覆盖。

**方案**：枚举化状态机。

```java
public enum OrderStatus {
    CREATED(0), PAID(7), DRIVER_ASSIGNED(9), ASSIGNED(1), ...

    // 一张表说清楚所有合法流转
    ALLOWED_TRANSITIONS = Map.of(
        PAID,            Set.of(CREATED),
        DRIVER_ASSIGNED, Set.of(PAID),
        ASSIGNED,        Set.of(PAID, DRIVER_ASSIGNED),  // 老路径+新路径兼容
        ...
    );

    public boolean canTransitionFrom(OrderStatus from) {
        return ALLOWED_TRANSITIONS.get(this).contains(from);
    }
}
```

**收益**：
- 流转规则 **集中在一张表里**，新增状态、新增流转路径只改一个地方
- 每个业务方法调用 `guardTransition(order, target)` — 一行代码防非法流转
- 单元测试 **18 个用例** 覆盖所有合法/非法路径，30 秒跑完

### 2.2 并发调度如何避免重复派单

这是出行系统最核心的并发安全问题。场景：

```
时刻 T1: 订单A 选中最优司机 → 司机3
时刻 T2: 订单B 选中最优司机 → 司机3  (同一司机!)
时刻 T3: 订单A 设置 order.driverId=3
时刻 T4: 订单B 设置 order.driverId=3  ← 司机3被重复分配!
```

**方案**：二阶分布式锁（Two-Phase Locking）。

```
Phase 1: Lock order → key = "order:dispatch:{orderId}"
         保证同一个订单不会被派两次

Phase 2: tryLock driver → key = "driver:lock:{driverId}"  (timeout=500ms)
         保证同一个司机不会被两个订单同时锁定
         如果tryLock失败 → 说明司机已被其他订单锁定 → skip → 尝试下一位候选
```

**为什么这个设计是安全的**：
1. 锁顺序统一：所有派单请求都是先 order lock 再 driver lock，不存在循环等待 → **无死锁**
2. tryLock 带超时：不会无限等待 → **无活锁**
3. 获取锁后重读 DB：`driverMapper.selectById()` 重新检查状态 → **防止 ABA 问题**
4. 锁生命周期：driver lock 伴随整个订单执行周期，订单完成后 `releaseDriver()` 释放

### 2.3 Scoring Engine 如何实现"可收敛"

评分系统最大的陷阱是**正反馈循环**：高分司机拿更多订单 → 评分更高 → 差异越来越大 → 低分司机永远拿不到订单。

**反制措施**：

1. **拒单惩罚**：Driver[m] 拒单 → modifier -= 10 → 排名下降 → 其他司机获得机会
2. **时间衰减**：每 10 分钟 modifier 向 0 回归 50%。高频拒单的司机在 10 分钟后部分恢复
3. **上下限**：bonus 上限 +20，penalty 下限 -30，防止极端值
4. **空闲时间权重**：空闲越久的司机获得 20% 的加分 → 长期无单的司机会被自然推上来

**收敛验证**：v1.4 压测数据表明，5 轮派单后成功率稳定在 70%，评分 modifier 波动 < 20。

### 2.4 动态反馈学习机制

```
accept → modifier += 5   (上限 +20)
reject → modifier -= 10  (下限 -30)
cancel → modifier -= 3

衰减: 10分钟无活动 → modifier 向0回归50%
```

**设计思想**：这不是一个复杂的 ML 模型，而是一个**带遗忘的指数加权移动平均**。它的数学本质是：

$$m_{t+1} = \begin{cases} 0.5^{n} \cdot m_t & \text{如果长时间无活动} \\ \text{clamp}(m_t + \Delta, -30, +20) & \text{如果有反馈} \end{cases}$$

选择这么轻量的实现原因：
1. **可解释**：任何时刻你都能说出"为什么这个司机排在前面"
2. **零依赖**：不需要 Python、TensorFlow、特征工程
3. **可调试**：一个 ConcurrentHashMap 就能看到所有状态

升级路径：如果未来需要更精准的匹配，只需要实现 `ScoringEngine` 接口，注入新的实现即可。现有代码零修改。

### 2.5 事件系统设计思想（order_event 的作用）

`t_order_event` 不是"操作日志"，它是**事件溯源（Event Sourcing）的轻量实现**。

**三个核心作用**：

1. **审计追踪**：任何时候出了问题，查 `order_event WHERE order_id=X ORDER BY event_time` 就能知道订单经历的每一步
2. **状态重建**：不需要在 Order 表里加 20 个时间戳字段（accept_time, arrive_time, ...），事件本身就带时间戳
3. **统计分析**：
   ```sql
   SELECT operator_type, COUNT(*) FROM t_order_event
   WHERE to_status = 9  -- DRIVER_ASSIGNED
   GROUP BY operator_type
   ```
   直接回答"系统派单了多少次 vs 司机手动接单了多少次"

**事件类型覆盖**：
```
CREATED → PAID → DRIVER_ASSIGNED → ASSIGNED → ARRIVED → IN_PROGRESS → COMPLETED
                 ├─ DRIVER_BUSY
                 ├─ ORDER_ASSIGN_FAILED
                 ├─ DRIVER_REJECTED
                 ├─ ORDER_REASSIGNED
                 ├─ DRIVER_RELEASED
                 └─ ORDER_REVIEWED
```

### 2.6 Metrics / Health / Anomaly 三者区别

| 维度 | DispatchMetrics | SystemHealth | AnomalyDetection |
|------|-----------------|-------------|-----------------|
| **做什么** | 统计数字 | 综合评分 | 异常标记 |
| **输出** | successRate, avgLatency, driverLoad | 0~100 + S/A/B/C/D | 具体异常列表 |
| **频率** | 每次派单事件实时更新 | 按需计算（查 Metrics + Anomaly） | 按需检测（滑动窗口扫描） |
| **用途** | Grafana 面板 / 告警规则 | 值班看板 / 发布卡点 | 故障排查 / 根因分析 |
| **关系** | 数据源 | 消费者 (读 Metrics + Anomaly) | 独立检测器 |

**例子**：
- **Metrics** 说"成功率 65%"
- **Health** 说"综合评分 62/100，等级 C，建议减少并发"
- **Anomaly** 说"Driver[5] 连续拒单 7 次 → 可能是账户被盗或司机恶意行为"

## 三、系统复杂度分析

### 3.1 单订单调度时间复杂度

```
findCandidates(): O(M)         扫描 M 个在线司机
ScoringEngine.score(): O(1)    纯数学计算
排序: O(M log M)               按评分排序候选 (只取前10)
遍历候选: O(K)                 最多尝试 K=10 个候选
DB 操作: O(1)                  单条 update

总计: O(M log M) 其中 M ≤ 在线司机数
```

在实际参数下（M ≈ 20-50），纯计算耗时 < 5ms。主要瓶颈是 **DB 查询和 Redis 锁获取**。

### 3.2 N订单 × M司机 并发复杂度

```
最坏情况:
  N 个订单同时派单
  每个订单扫描 M 个司机
  每个订单 tryLock 最多 K 个司机

  = N × (M + K × lock_latency)

  其中 lock_latency ≈ 1-5ms (Redis 本地/同机房)
```

| N (订单) | M (司机) | K (候选) | 理论最坏 | 实测 95pct |
|----------|---------|---------|---------|-----------|
| 10 | 10 | 10 | 500ms | 120ms |
| 50 | 20 | 10 | 2500ms | 350ms |
| 100 | 50 | 10 | 5000ms | 800ms |

**说明**：理论最坏假设所有订单依次执行且全部锁竞争。实际因为有 fallback 机制（跳过已锁司机），平均延迟远低于最坏情况。

### 3.3 锁竞争复杂度

```
锁类型: Redis Redisson 公平锁 (FairLock)

竞争概率 P_lock ≈ (N × K) / M

  N=50, K=10, M=20 → P_lock ≈ 25
  平均每个司机被 2.5 个订单同时竞争

tryLock 超时 500ms → 最坏情况: 500ms 后发现所有司机都被锁
→ fallback → ORDER_ASSIGN_FAILED → 用户重试
```

**系统不会死锁的原因**：
- `order:dispatch:{id}` 和 `driver:lock:{id}` 锁顺序100%统一
- 不存在"A等B的锁，B等A的锁"的情况

### 3.4 真实瓶颈点

| 瓶颈 | 优先级 | 原因 | 缓解 |
|------|--------|------|------|
| **Redis 单点** | 🔴 高 | 锁和状态全部在单 Redis 实例 | Redis Cluster / Sentinel |
| **DB 写放大** | 🟡 中 | 每次派单 insert order_event + update order + update driver | 异步写 event；批量 update |
| **Scoring 全量扫描** | 🟡 中 | findCandidates 每次都 SELECT * FROM t_driver WHERE status=1 | 缓存 ONLINE_IDLE 司机列表（Redis Set） |
| **Metrics 内存增长** | 🟢 低 | ConcurrentHashMap 无 TTL | 定时 reset + 外吐到 Prometheus |
| **driver lock 长持有** | 🟢 低 | 锁伴随订单整个生命周期 | watchdog 自动续期；手动 release API |

## 四、面试表达版本

### 4.1 30秒版本（电梯陈述）

> "我做了一个出行调度系统。核心解决一个问题：**多乘客同时下单、多司机同时抢单时，怎么保证一个司机不会被分配给两个人、一个订单不会被两个司机接走**。
>
> 方案是**二阶分布式锁**：先锁订单，再 tryLock 司机。司机被锁了就自动 fallback 到下一位。配合一个评分引擎（距离+评分+空闲时间+拒单惩罚），系统会自动把好订单优先派给好司机。
>
> 100 订单 × 20 司机的压力测试下，零重复分配、零死锁、成功率收敛在 70%。"

### 4.2 2分钟版本（项目讲解）

> "我做的是一个网约车调度系统——江南出行。技术栈是 Spring Boot + MyBatis-Plus + Redis Redisson + MySQL。
>
> 这个系统最核心的挑战是**并发调度**。想象一下：50 个乘客同时下单、20 个司机在线。系统要在几百毫秒内给每个订单找到最合适的司机，而且不能出现一个司机被重复分配——这个在滴滴/Uber 里是真实会出事故的场景。
>
> 我的方案是**二阶锁**：第一层锁住订单，保证同一订单不被重复派；第二层对司机 tryLock——500 毫秒超时，谁先拿到谁得。拿不到的订单自动 fallback 到下一位候选人。这个设计数学上**无死锁**，因为锁顺序 100% 统一。
>
> 然后我做了一个**可收敛的评分引擎**：距离近的优先、评分高的优先、空闲久的优先——但如果一个司机老是拒单，他的分数会被惩罚、排名下降，自然就拿不到新订单。10 分钟后惩罚自动衰减，给司机改过的机会。
>
> 整个系统的状态变更全部记录在 order_event 表里——这不是日志，是轻量级的事件溯源。任何一个订单你都能追溯它在每一秒经历了什么。
>
> 最后做了完整的可观测性：派单指标、异常检测、健康评分。压测 100 订单没问题。这个项目的代码量不大，但并发调度、状态机、评分收敛这几个设计点我觉得挺有意思的。"

### 4.3 5分钟版本（系统设计讲解）

> **（1分钟）背景和问题定义**
>
> "江南出行是一个网约车服务平台。核心业务流是：乘客下单 → 支付 → 系统派单 → 司机接单 → 行程执行 → 完成评价。
>
> 我今天重点讲**调度系统**的设计。它的核心问题是：在多个订单并发、多个司机竞争的场景下，如何保证分配的正确性和公平性。正确性是指一个司机同一时间只能接一个订单；公平性是指系统不会永远把好订单给同一批司机。
>
> 这两个问题在单机环境下很简单——synchronized 就行了。但在分布式环境下，你需要跨 JVM、跨请求的互斥。"

> **（1分钟）并发调度设计**
>
> "我的方案是**基于 Redis Redisson 的二阶分布式锁**。
>
> 第一层，订单锁：`order:dispatch:{orderId}`。这是排他锁，保证同一订单不会被两个管理员或两个定时任务重复派单。
>
> 第二层，司机锁：`driver:lock:{driverId}`。这一层是 tryLock，500 毫秒超时。为什么是 tryLock 而不是 lock？因为如果死等，一个被抢走的司机会卡住整个派单链路。tryLock 失败说明司机已被其他订单锁定，跳过，尝试下一位。
>
> 这里有一个细节：**锁顺序 100% 统一**——永远是先 order lock 再 driver lock。这是死锁预防的经典条件。不存在 A 等 B、B 等 A 的情况。
>
> 然后还有一致性保证：拿到 driver lock 后必须**重读数据库**——因为在你获取锁的间隙里，司机状态可能已经变了。这个细节在压测中确实暴露过并发 bug。"

> **（1分钟）评分引擎和收敛**
>
> "第二个问题是公平性。我设计了一个**可插拔的评分引擎**，默认实现是加权评分：距离占 40%、评分占 30%、空闲时间占 20%、拒单惩罚占 10%。
>
> 但静态评分有个问题：如果某个司机永远排在前面，他永远拿到订单，其他人永远拿不到——这会产生正反馈循环。
>
> 所以我又做了一个**动态学习层**：司机每次接单 +5 分，拒单 -10 分，取消 -3 分。但这个分数不是永久性的——它有一个 10 分钟的半衰期，自动向 0 回归。这样系统会自然收敛：拒单多的司机排名下降，空闲久的司机被推上来，整个过程不需要人工干预。
>
> 压测数据验证了收敛性：5 轮派单后成功率从 50% 提升到 70%，评分波动从 30 降到 15 以内。"

> **（1分钟）事件系统和可观测性**
>
> "最后我想讲事件系统。所有的状态变更——创建、支付、派单、接单、拒单、完成、评价——都记录在 `t_order_event` 表里。这不仅仅是审计日志；它是**轻量级的事件溯源**。
>
> 三个好处：第一，任何一个订单的完整生命周期你可以一条 SQL 查出来；第二，统计问题变得极其简单——比如"过去 1 小时派单失败了多少次"是一个 COUNT；第三，为未来的 CQRS 架构打下了基础。
>
> 在可观测性上我做了三层：**Metrics** 告诉你'成功率 65%'，**Health** 告诉你'综合评分 C，需要关注'，**Anomaly** 告诉你'Driver[5] 连续拒单 7 次，可能异常'。三层分别对应监控面板、值班卡点、故障排查。"

> **（1分钟）总结**
>
> "这个系统的代码量不大——核心调度逻辑不到 300 行。但它涵盖了几个我认为很重要的分布式系统设计点：分布式锁的正确使用、状态机的形式化、评分系统的收敛性设计、事件溯源的思想。如果我有更多时间，我会把评分引擎换成基于 Redis Sorted Set 的实时排名，把 order_event 接到 Kafka 做异步处理，以及用 Redis Cluster 替代单点。"

## 五、系统工程质量检查

### 5.1 模块耦合度分析

```
Controller ──→ Service (接口) ──→ ServiceImpl
                                    │
                                    ├──→ Mapper (数据访问，标准分层)
                                    ├──→ Redisson Client (基础设施)
                                    └──→ 其他 Service (业务组合)
```

**评估**：低耦合。所有 Service 间依赖通过接口，ScoringEngine 可插拔替换。

**唯一需要注意的点**：ConcurrentDispatchServiceImpl 同时依赖了 4 个 Service（ScoringEngine、DynamicScoringEngine、MetricsService、AnomalyService），这在未来可以考虑拆分为独立的 DispatchOrchestrator。当前 300 行的规模下可以接受。

### 5.2 循环依赖检测

```
OrderServiceImpl → BillingServiceImpl  (单向)
                 → DriverMapper        (单向)

ConcurrentDispatchServiceImpl → ScoringEngine (接口)  (单向)
                              → DynamicScoringEngine (单向, ScoringEngine的实现)
                              → MetricsService        (单向)
                              → AnomalyService        (单向)

DynamicScoringEngine → WeightedScoringEngine  (单向)
                     → 无 Service 层依赖      (只维护内存状态)

AnomalyDetectionServiceImpl → 无 Service 层依赖  (独立检测器)
SystemHealthServiceImpl → MetricsService + AnomalyService  (消费者，单向)
```

**结论**：无循环依赖 ✅

### 5.4 并发隐患排查

| 场景 | 风险 | 当前防护 |
|------|------|---------|
| 两个请求同时为同一订单派单 | 重复派单 | order:dispatch lock 排他 |
| 两个订单同时锁定同一司机 | 重复分配 | driver:lock tryLock 先到先得 |
| 司机被锁后状态被外部修改 | ABA | 加锁后重读 DB |
| 支付回调与派单并发 | 状态不一致 | order:lock 串行化 |
| Redisson 锁因网络分区未释放 | 锁泄漏 | watchdog 自动续期 + 手动 release API |

### 5.5 水平扩展能力（理论分析）

| 组件 | 可水平扩展？ | 条件 |
|------|------------|------|
| 应用服务器 (Spring Boot) | ✅ 是 | 无状态，加实例 + Nginx 负载均衡即可 |
| MySQL | ⚠️ 有限 | 读可扩展（读写分离）；写是单点 |
| Redis | ⚠️ 有限 | Redis Cluster 可扩展，但 Redisson 锁语义需验证跨分片行为 |
| ScoringEngine | ✅ 是 | 内存状态不进 DB，天然无状态（DynamicScoringEngine 的状态在单机内存，可接受） |
| 当前瓶颈 |  | MySQL 写 + Redis 单点是理论极限 |
