## 一、调度与并发

### Q1：为什么使用 Redis 分布式锁？

**参考回答**：

因为调度场景是跨请求的互斥。一个司机被分配后，可能在任意时间被其他订单尝试分配——这不是单个请求内的 synchronized 能解决的。

选 Redisson 而不是手写 Lua 脚本，因为 Redisson 提供了 tryLock、公平锁、读写锁这些高级原语，还自带看门狗续期机制。我的二阶锁方案如果换成 Jedis + 手写 Lua，代码量和出错概率会大很多。

关键细节：我用的是 tryLock（500ms 超时）而不是 lock（无限等待）。因为调度场景下，拿不到锁说明司机正在被其他订单处理，应该快速 fallback 到下一位候选，而不是阻塞等待。

---

### Q2：如何避免重复派单？

**参考回答**：

二阶分布式锁。

**Phase 1**：锁订单 `order:dispatch:{orderId}`——保证同一个订单不会被派两次。这是排他锁，同一订单的并发请求会被串行化。

**Phase 2**：tryLock 司机 `driver:lock:{driverId}`（500ms 超时）——保证同一个司机不会被两个订单同时锁定。如果 tryLock 失败，说明司机已被其他订单锁定，自动 skip 到下一位候选。

关键保障：
1. 锁顺序 100% 统一（永远先 order 再 driver）——数学上无死锁（破坏循环等待条件）
2. tryLock 超时机制——无活锁
3. 加锁后重读 DB——防 ABA 竞态
4. 所有候选失败——记录 ORDER_ASSIGN_FAILED 事件

压测验证：100 订单 × 20 司机，零重复分配、零丢失、零死锁。

---

### Q3：为什么是二阶锁而不是一阶锁？

**参考回答**：

一阶锁解决不了问题。如果只锁订单，两个订单可以同时选中同一个司机——因为司机资源是共享的。如果只锁司机，订单可能被重复派发——因为没有机制阻止两个请求同时处理同一订单。

二阶锁的本质是：**先锁定任务（订单），再竞争资源（司机）**。这保证了：
- 同一订单不会被两个线程同时处理（Phase 1）
- 同一司机不会被两个订单同时锁定（Phase 2）

锁顺序统一（order → driver）是死锁预防的经典条件：不存在 A 等 B、B 等 A 的循环等待。

---

### Q4：锁超时为什么是 500ms？

**参考回答**：

这是权衡值。

太短（如 50ms）：高碰撞率下大量 tryLock 失败，导致 fallback 频繁，实际分配效率下降。
太长（如 5s）：请求排队，调度延迟增加，用户体验差。

500ms 的依据：
- 司机分配操作本身（DB 更新 + 事件记录）约 20-50ms
- 加上网络往返和锁竞争，500ms 足够覆盖正常情况
- 超过 500ms 基本意味着异常（如 GC 停顿、DB 慢查询），此时 fallback 比等待更合理

实际压测中，500ms 超时下 20 司机竞争场景的 fallback 率约 15%，可接受。

---

### Q5：有没有更简单的方案？

**参考回答**：

有，但各有取舍。

**方案 1：单机 synchronized**。如果只有一个 JVM 实例，synchronized 足够。但无法水平扩展，单点故障。

**方案 2：数据库乐观锁**。司机表加 version 字段，CAS 更新。但出行场景司机资源稀缺，碰撞率必然高，乐观锁重试成本大。

**方案 3：分片方案**。按城市分区，每个城市独立调度，降低竞争。但通用性不如二阶锁，且跨城订单需要特殊处理。

我选二阶锁是因为：通用性强、可水平扩展、碰撞率高时表现稳定。实际生产中可以结合分片——按城市分片 + 片内二阶锁。

---

### Q6：如何扩展到百万级订单？

**参考回答**：

当前瓶颈在三个地方，对应三个优化方向。

**瓶颈 1：findCandidates 全表扫描**。当前每次调度都 SELECT * FROM t_driver WHERE status=1。万级司机时这是 O(N) 扫描。
**优化**：用 Redis Sorted Set 实时维护在线司机排名，O(log N) 查询。司机上线/下线/状态变更时同步更新 ZSet。

**瓶颈 2：单机 Redis 锁**。Redis 单点是吞吐上限。
**优化**：Redis Cluster 分片。按 driverId hash 分片，不同司机的锁落在不同节点，吞吐线性扩展。

**瓶颈 3：同步事件写入**。order_event 同步 INSERT 影响调度延迟。
**优化**：事件写入改异步——先发 Kafka，下游消费者持久化。调度主链路不再受事件写入影响。

百万级还需要：MySQL 读写分离、订单分表（按城市/时间）、监控告警体系完善。但核心调度逻辑不需要大改——因为 ScoringEngine 是接口、事件系统是独立表、锁机制不依赖评分实现。

---

### Q7：为什么当前不用 MQ？

**参考回答**：

因为当前规模不需要。

MQ 的核心价值是解耦和异步。当前场景下：
- 订单量不大（压测 100 订单），同步处理延迟可接受（< 150ms）
- 事件写入 order_event 是 INSERT 操作，本身很快（< 5ms）
- 引入 MQ 会增加运维复杂度（Broker 部署、消费保证、幂等处理）

但架构上已经为 MQ 铺了路：order_event 表就是天然的消息源。未来把事件写入改成发 Kafka，下游消费者负责持久化和统计——业务代码不需要改。

这是"先做对，再做快"的思路：当前用同步保证正确性，架构上保留异步化的可能性。

---

### Q8：并发测试怎么做的？

**参考回答**：

不是"看起来正常"，是数学证明无重复。

压测脚本：100 个订单并发提交，20 个司机在线。每个订单触发完整的调度流程（锁 → 评分 → 分配 → 事件记录）。

验证方式：
1. **driverId 唯一性**：所有已分配订单的 driverId 集合大小 == 已分配订单数（无重复）
2. **订单完整性**：所有订单最终状态为 ASSIGNED 或 ORDER_ASSIGN_FAILED（无丢失）
3. **司机状态一致性**：被分配的司机状态为 BUSY，未被分配的为 ONLINE_IDLE
4. **事件完整性**：每个分配都有对应的 DRIVER_ASSIGNED 事件

关键：不是看"有没有报错"，是验证不变量（invariant）。分布式系统的正确性必须靠不变量验证，不能靠观察。

## 二、状态机与一致性

### Q9：为什么设计状态机？

**参考回答**：

因为订单生命周期有 10 个状态、15+ 条合法流转路径。用 if-else 会有两个致命缺陷：

1. **流转规则不可见**：你看任何一个方法的代码，都无法知道完整的合法流转是什么。排查 bug 需要全局搜索所有 setStatus 调用。
2. **流转规则不可测试**：你无法单独验证"从 CREATED 能否跳到 COMPLETED"，只能通过集成测试覆盖。

状态机方案：枚举 + 流转表（Map<OrderStatus, Set<OrderStatus>>）。所有合法路径集中在一张表里，每个业务方法调用 guardTransition() 一行代码防非法流转。

收益：18 个单元测试覆盖所有合法/非法路径，30 秒跑完。新增状态只改 1 个枚举文件。

---

### Q10：如何保证订单状态一致？

**参考回答**：

三个层面。

**第一层：状态机 guard**。每次状态变更前调用 guardTransition()，非法流转直接抛异常。这是第一道防线——业务代码无法绕过。

**第二层：事务原子性**。状态变更和事件记录在同一个事务里——要么都成功，要么都回滚。不会出现"状态变了但事件没记录"的情况。

**第三层：事件溯源审计**。所有状态变更都记录在 order_event 表，包含 from_status、to_status、event_type、operator、event_time。即使状态被篡改，事件记录不可篡改——一条 SQL 回溯完整生命周期。

这三层保证：状态变更合法（guard）、一致（事务）、可追溯（事件溯源）。

---

### Q11：订单状态和司机状态怎么同步？

**参考回答**：

通过业务方法中的显式联动。

例如 cancelOrder 方法：
1. guardTransition(order, CANCELLED) — 校验订单能否取消
2. order.setStatus(CANCELLED) — 更新订单状态
3. 如果 order.driverId 存在且司机状态为 BUSY → driver.setStatus(ONLINE_IDLE) — 恢复司机
4. 记录 ORDER_CANCELLED 事件 + DRIVER_RELEASED 事件
5. 事务提交

关键：这些操作在同一个事务里。如果司机恢复失败，整个事务回滚——订单也不会被取消。这保证了订单状态和司机状态的原子性一致。

早期版本有 bug：取消订单时没有恢复司机状态，导致司机永远卡在 BUSY 状态无法接新单。修复后加入了显式的司机状态恢复逻辑。

---

### Q12：ABA 问题是什么？怎么遇到的？

**参考回答**：

ABA 问题：线程 A 读取司机状态为"空闲"，线程 B 在此期间将其改为"忙碌"又改回"空闲"，线程 A 拿到锁后仍认为"空闲"——但这个"空闲"已经不是刚才读到的那个"空闲"了。

我在压测中真实遇到：两个订单同时选中司机 3。订单 A 拿到 driver:lock:3，分配成功。订单 A 释放锁后，订单 B 拿到锁——但订单 B 在加锁前读到的司机状态是"空闲"（其实是订单 A 分配前的旧状态）。订单 B 基于过期状态做决策，导致重复分配。

修复方案：加锁后重读 DB。tryLock 成功后，重新 SELECT 司机状态，如果不再是"空闲"则 skip。这是乐观锁的思想——锁保证互斥，重读保证数据新鲜。

## 三、数据库设计

### Q13：为什么这样设计数据库？

**参考回答**：

三条原则。

**第一，一表一职责**。t_order 管订单，t_payment 管支付，t_driver 管司机，t_review 管评价——每张表只做一件事。不搞大宽表，避免更新异常。

**第二，事件与状态分离**。订单的当前状态存在 t_order.status 里，但状态的变化过程存在 t_order_event 里。这是轻量级事件溯源。好处：查一个订单经历了什么，一条 SELECT 就能回溯全流程，不需要在订单表加 20 个时间戳字段。

**第三，迁移脚本版本化管理**。init.sql 是建表脚本，migration_v1.1、v1.2、migration_optimize、migration_state_machine 是增量变更。团队协作中不会出现"你的数据库和我的不一样"。

27 张表覆盖了用户体系、订单体系、支付体系、司机体系、营销体系、AI 体系、风控体系和消息体系。

---

### Q14：为什么用事件溯源？和操作日志有什么区别？

**参考回答**：

本质区别在于**结构化**。

操作日志：记录"谁在什么时间做了什么操作"，通常是字符串拼接，不可查询、不可分析。比如 log.info("订单{}状态变更为{}", id, status)。

事件溯源：记录结构化的事件——from_status、to_status、event_type、operator、event_time、metadata。每条事件都有明确的类型和字段。

收益：
1. **可查询**：SELECT * FROM t_order_event WHERE event_type='DRIVER_REJECTED' AND driver_id=3 — 查某司机的拒单记录
2. **可统计**：统计"系统派单 vs 司机手动接单"比例无需联表查询
3. **可回溯**：一条 SQL 回溯任意订单的完整生命周期
4. **为 CQRS 铺路**：未来可以把事件流接到 Kafka，下游做读模型投影

这不是完整的 Event Sourcing（不重建状态），是轻量级版本——只记录不重建。但已经比操作日志强很多。

---

### Q15：索引怎么设计的？

**参考回答**：

按查询场景设计。

- **t_order**：user_id（用户查订单）、driver_id（司机查订单）、status（按状态筛选）、create_time（时间范围）。复合索引 (user_id, status, create_time) 覆盖最常见的"查某用户某状态的近期订单"。
- **t_driver**：status（找空闲司机）、location 相关字段（地理查询）。复合索引 (status, is_online) 覆盖"在线空闲司机"查询。
- **t_order_event**：order_id（查订单事件流）、event_type（按事件统计）。复合索引 (order_id, event_time) 覆盖"回溯订单生命周期"。

原则：遵循最左前缀原则，避免冗余索引，大表必分页（默认 10 条/页）。

## 四、架构演进

### Q16：单体架构如何演进？

**参考回答**：

当前是单体架构（Spring Boot 单应用），但架构上已经为演进铺了路。

**演进路径**：

1. **阶段 1（当前）**：单体，所有模块在一个 JVM。适合 MVP 和验证业务逻辑。
2. **阶段 2**：按模块拆分微服务——订单服务、调度服务、支付服务独立部署。服务间通过 REST 或 gRPC 通信。
3. **阶段 3**：引入消息队列（Kafka）解耦。order_event 天然适合作为消息源，下游消费者做统计、风控、数据仓库。
4. **阶段 4**：调度服务独立扩展。按城市分片，每个城市独立的调度实例 + Redis Cluster 分片。

当前架构的好处：接口化设计（ScoringEngine 是接口）、事件化设计（order_event 独立表）、无状态应用（可水平扩展）。这三个设计让未来演进不需要大改业务代码。

---

### Q17：ScoringEngine 为什么设计成接口？

**参考回答**：

开闭原则——对扩展开放，对修改关闭。

当前有两个实现：
- WeightedScoring：静态评分（距离 40% + 评分 30% + 空闲 20% + 拒单 10%）
- DynamicScoring：在静态评分上叠加动态 modifier

接口化的好处：
1. **策略可插拔**：换评分策略只需要实现新类 + 改一行注入配置，调度主逻辑不变
2. **可测试**：可以 Mock ScoringEngine 测试调度流程，不依赖具体评分实现
3. **可演进**：未来加机器学习评分模型，只需要新实现一个类

DynamicScoring 用 @Primary 注解标记为默认实现，Spring 自动注入。如果未来要切回静态评分，去掉 @Primary 加到 WeightedScoring 上即可。

---

### Q18：动态评分的 modifier 存哪里？

**参考回答**：

当前存在内存（ConcurrentHashMap<driverId, modifier>）。

这是 demo 级别设计——重启后 modifier 丢失，司机从零开始。

生产环境的改进方案：
1. **Redis 持久化**：modifier 存 Redis，TTL 设为半衰期的几倍（如 30 分钟）。重启后从 Redis 恢复。
2. **定期快照到 DB**：每 5 分钟把 modifier 快照到 t_driver_score_modifier 表。重启时从 DB 恢复。
3. **事件驱动重建**：从 order_event 表重放最近的接单/拒单事件，重建 modifier。最准确但启动慢。

当前选内存是因为：demo 场景重启频率低、modifier 丢失影响不大（系统会快速重新收敛）。生产环境会用方案 1（Redis 持久化）。

---

### Q19：如何保证系统可扩展？

**参考回答**：

三层考虑。

**代码层面**：ScoringEngine 是接口，替换策略只需实现新类。新增订单状态只需枚举加 1 行 + 流转表加 1 个 entry。开闭原则。

**架构层面**：事件系统（order_event）为异步化铺路。未来接入 Kafka，下游消费者做实时统计、风控告警、数据仓库——不需要改业务代码。

**部署层面**：Spring Boot 应用无状态，加实例 + Nginx 负载均衡即可水平扩展。瓶颈在 MySQL 写和 Redis 单点——生产环境 MySQL 读写分离，Redis Cluster 模式。

还有一点：状态机是形式化的，不是散落 if-else——新来的开发者可以快速理解系统行为，不需要读遍所有 Service 代码。这降低了团队扩展的认知成本。

---

### Q20：10 分钟半衰期是怎么确定的？

**参考回答**：

权衡值，基于业务场景。

太短（如 1 分钟）：modifier 频繁归零，等于没有动态学习——司机刚拒单扣的分马上就回来了。
太长（如 1 小时）：modifier 长期影响排序，一次拒单影响太久——惩罚过重。

10 分钟的依据：
- 出行场景的高峰期通常持续 30-60 分钟，10 分钟半衰期意味着一个高峰期内 modifier 会有显著影响
- 司机的"短期状态"（如临时不想接单）通常持续几分钟到十几分钟，10 分钟半衰期刚好覆盖
- 上下限 (-30, +20) 配合半衰期，保证极端情况下 modifier 也会在 30 分钟内基本归零

实际压测：5 轮派单（约 10-15 分钟）后系统收敛。如果半衰期改为 1 分钟，收敛更快但震荡严重；改为 1 小时，收敛太慢。

## 五、AI 与工程实践

### Q21：AI 如何参与开发？

**参考回答**：

全程使用 Claude Code 辅助，AI 参与度约 60%。

**分工**：
- **人工负责**（40%）：架构决策、并发设计、状态机形式化、评分收敛分析、规则约束制定
- **AI 负责**（60%）：代码生成、测试编写、文档撰写、code review、重复性工作

**关键原则**：不是让 AI 替你做决定，是让 AI 帮你做执行层的工作。我负责判断和决策，AI 负责生成代码。这个分工很关键。

**约束体系**：建立了 20 条规则约束 AI 行为（编码前先思考、简洁优先、外科手术式修改、目标驱动执行等），比每次口头纠正高效得多。

---

### Q22：AI 会不会写出 bug？

**参考回答**：

会，而且确实遇到过。

典型例子：AI 生成代码时没有考虑加锁后重读 DB，导致 ABA 问题。AI 基于已有逻辑生成代码，但不知道业务场景中存在并发竞态——这需要人工判断。

应对方式：
1. **关键路径人工审查**：并发、锁、状态机这些关键逻辑，AI 生成后我逐行审查
2. **测试驱动**：先写测试（压测脚本、不变量验证），再让 AI 写实现。测试不通过就重写
3. **规则约束**：在 CLAUDE.md 中明确"加锁后必须重读 DB"这类规则，AI 生成时会遵守

AI 是放大器——好工程师用 AI 更高效，差工程师用 AI 写出更多 bug。关键还是人判断。

### Q23：如何保证代码质量？

**参考回答**：

四道防线。

**第一道：测试先行**。遵循 RED → GREEN → REFACTOR。先写测试（必须失败），再写最小实现（必须通过），再重构。81 个后端测试 + 155 个前端测试，100% 通过。

**第二道：Code Review**。每个 Task 完成后自动进行 Code Review，多维度审查（正确性、安全性、性能、可维护性）。

**第三道：规则约束**。20 条编码规则（简洁优先、外科手术式修改、失败必须显性化等）写入 CLAUDE.md，AI 生成代码时自动遵守。

**第四道：压测验证**。并发场景的不变量验证（driverId 唯一性、订单完整性、司机状态一致性）。不是"看起来正常"，是数学证明无重复。

### Q24：为什么选择 Spring Boot + MyBatis-Plus？

**参考回答**：

选型考虑三点。

**Spring Boot**：Java 生态的企业级标准，依赖注入、自动配置、AOP、事务管理都是开箱即用。对于需要事务一致性的订单和支付系统，Spring 的声明式事务是刚需。

**MyBatis-Plus**：比 JPA 更灵活。出行系统的查询场景复杂——按状态筛选、按时间范围、按地理位置排序。MyBatis-Plus 的 Lambda 条件构造器比 JPA 的 Criteria API 更直观，而且支持原生 SQL——复杂查询不会被 ORM 限制。

**Redisson**：不是简单的 Redis 客户端——它提供分布式锁、公平锁、读写锁这些高级原语。我的二阶锁方案如果换成 Jedis + 手写 Lua 脚本，代码量和出错概率会大很多。

每个选型都有明确的工程理由，不是"哪个流行用哪个"。

## 六、综合问题

### Q25：这个项目最难的地方是什么？

**参考回答**：

最难的是并发调度的一致性保证。

场景：50 个乘客同时下单、20 个司机在线。系统要在几百毫秒内给每个订单找到最合适的司机，而且必须保证一个司机不会被两个订单同时分配——这在分布式环境下不是一把 synchronized 能解决的。

方案是二阶分布式锁。第一层锁订单保证不重复派，第二层 tryLock 司机——500 毫秒超时，拿到就分配，拿不到自动 fallback 下一位。

关键细节是锁顺序必须 100% 统一——永远先 order 锁再 driver 锁。这是死锁预防的经典条件：不存在 A 等 B、B 等 A 的循环等待。另外加锁后必须重读数据库——因为在你获取锁的间隙里，司机状态可能已经被其他线程改了。这个 ABA 问题是我在压测中真实遇到的，修复后就没再出现过。

100 订单 × 20 司机压测验证：零重复分配、零死锁。

---

### Q26：如果重做你会优化什么？

**参考回答**：

三个优化方向。

**第一，评分引擎实时化**。当前 findCandidates 每次全表扫描。重做会用 Redis Sorted Set 实时维护在线司机排名，O(log N) 查询。

**第二，事件系统异步化**。当前 order_event 同步写入。重做会改成 Kafka 异步——先发消息，下游消费者持久化。调度延迟不受事件写入影响。

**第三，评分引擎接入真实数据**。当前收敛验证依赖模拟压测。接入真实运营数据可以做 A/B 测试——对比"有衰减"和"无衰减"两组司机的长期接单率差异。

但当前架构不需要大改——这三个优化都是增量式的，因为 ScoringEngine 是接口、事件系统是独立表、锁机制不依赖评分实现。

### Q27：这个项目最大的收获是什么？

**参考回答**：

三个收获。

**技术上**，真正理解了分布式锁的语义。不是"用了 Redisson"就完了——锁顺序为什么重要、tryLock 和 lock 的区别、ABA 问题怎么发生怎么防、死锁的必要条件——这些看书和实际写代码是完全不同的体验。

**工程上**，学会了"先设计再编码"。状态机的形式化、事件的溯源设计、评分的收敛分析——这些都不是写代码写出来的，是坐下来画图、列表、算复杂度得出的。如果一上来就写代码，大概率会写成 if-else 地狱。

**方法上**，验证了 AI 辅助开发的正确姿势。不是让 AI 替你做决定，是让 AI 帮你做执行层的工作——你负责判断和决策。而且建立规则约束 AI 的行为，比每次口头纠正高效得多。

### Q28：为什么用 tryLock 而不是 lock？

**参考回答**：

因为调度场景需要快速失败而不是阻塞等待。

lock() 是无限等待——拿不到锁就一直等。这在调度场景下是灾难：如果司机 3 被订单 A 锁定，订单 B 用 lock() 等待，会一直阻塞。如果司机 3 的锁因为某种原因不释放（如订单 A 处理慢、GC 停顿），订单 B 就卡死了。

tryLock(500ms) 是超时等待——500ms 拿不到就返回 false，订单 B 自动 fallback 到下一位候选司机。这保证了：
1. 调度延迟可控（最坏 500ms × 候选数）
2. 不依赖锁释放（即使锁持有方异常，也不会无限等待）
3. 高碰撞率下仍有吞吐（失败就换下一个，不堆积）

### Q29：支付幂等怎么做的？

**参考回答**：

双层幂等。

**第一层：Redisson 分布式锁**。锁 key 为 `pay:idempotent:orderId:userId`，TTL 10 秒。保证同一支付的并发请求被串行化——第二个请求拿到锁时，第一个已经完成。

**第二层：Redis 持久化幂等结果**。锁内先检查 `RBucket<Long>`（key 同上，TTL 24 小时）。如果命中，说明这个支付已经处理过，直接返回已有结果。如果未命中，执行支付逻辑，成功后写入 bucket。

为什么需要两层？锁只做并发控制（10 秒），锁释放后重试仍会创建重复支付。Redis bucket 做长期幂等（24 小时），即使锁释放后重试也能拦截。

幂等键格式 `pay:idempotent:orderId:userId`——按订单 + 用户维度，同一用户对同一订单的多次支付请求只成功一次。

### Q30：WebSocket 连接怎么限流？

**参考回答**：

用 AtomicInteger 全局连接计数器。

每个 WebSocket 端点维护一个 static AtomicInteger totalConnections。onOpen 时 incrementAndGet，如果超过阈值（如 1000）则 decrementAndGet 并关闭连接。onClose 时用 wasInMap 模式——只有 session 确实从 map 中移除时才 decrementAndGet，防止计数器变负。

三个端点的阈值：
- OrderTrackingServer：1000（订单追踪，乘客端）
- DriverLocationServer：500（司机位置，司机端，资源更紧张）
- NotificationWebSocketServer：1000（通知推送，全端）

为什么不用 Redis 分布式计数？因为当前是单机部署，AtomicInteger 足够且性能更好。生产环境多实例时可以改为 Redis INCR + Lua 脚本保证原子性。

wasInMap 模式是关键：早期版本直接 decrementAndGet 会导致计数器变负（onClose 可能在 onError 后重复触发），修复后只有真正从 map 移除 session 时才减计数。

### Q31：评分引擎的权重怎么确定的？

**参考回答**：

距离 40% + 评分 30% + 空闲 20% + 拒单 10%。

基于业务优先级：
- **距离 40%**：出行场景的核心体验是"司机快到"。距离近 = 等待时间短 = 体验好。最高权重。
- **评分 30%**：服务质量。高评分司机应该优先——但要小于距离，否则好司机永远忙不过来。
- **空闲 20%**：公平性。空闲久的司机应该被推上来，避免"富者愈富"。
- **拒单 10%**：惩罚性。拒单多的司机排名下降，但权重不高——因为拒单可能是有正当理由的（如堵车）。

这些是初始值，实际需要根据运营数据调参。DynamicScoring 的动态 modifier 就是补偿静态权重的不足——如果静态权重不合理，动态层会自动修正。

### Q32：为什么没有用消息队列？

**参考回答**：

当前规模不需要。

MQ 的核心价值是解耦和异步。当前场景下：
- 订单量不大（压测 100 订单），同步处理延迟可接受（< 150ms）
- 事件写入 order_event 是 INSERT 操作，本身很快（< 5ms）
- 引入 MQ 会增加运维复杂度（Broker 部署、消费保证、幂等处理）

但架构上已经为 MQ 铺了路：order_event 表就是天然的消息源。未来把事件写入改成发 Kafka，下游消费者负责持久化和统计——业务代码不需要改。

这是"先做对，再做快"的思路：当前用同步保证正确性，架构上保留异步化的可能性。过早引入 MQ 是过度设计。

### Q33：项目中最有意思的 bug 是什么？

**参考回答**：

ABA 问题。

压测时发现 100 订单中有 1-2 个出现重复分配。排查了很久——因为概率低，不是每次都复现。

根因：两个订单同时选中司机 3。订单 A 拿到 driver:lock:3，分配成功。订单 A 释放锁后，订单 B 拿到锁——但订单 B 在加锁前读到的司机状态是"空闲"（其实是订单 A 分配前的旧状态）。订单 B 基于过期状态做决策，导致重复分配。

修复：加锁后重读 DB。tryLock 成功后，重新 SELECT 司机状态，如果不再是"空闲"则 skip。

这个 bug 有意思的地方在于：它不是代码逻辑错误，是并发竞态。单线程测试永远不会发现，只有压测才能暴露。这让我深刻理解了"分布式系统的正确性必须靠不变量验证，不能靠观察"。

### Q34：如何快速定位线上问题？

**参考回答**：

靠事件溯源 + 可观测性。

**事件溯源**：一条 SQL 回溯订单完整生命周期。
```sql
SELECT * FROM t_order_event WHERE order_id = ? ORDER BY event_time;
```
能看到每个状态变更的时间、操作者、事件类型。如果订单卡在某个状态，能立即看到是哪个环节出了问题。

**Metrics**：成功率、平均延迟、司机负载分布。如果成功率突降，说明调度出问题；如果延迟飙升，说明锁竞争或 DB 慢查询。

**Health**：综合健康评分（S/A/B/C/D）。S 级正常，D 级需要立即介入。

**Anomaly**：连续拒单 ≥5、订单失败 ≥3、评分波动 >30、锁竞争 ≥10。自动告警，不需要人盯监控。

这三层覆盖了"发现问题（Metrics）→ 定位问题（Anomaly）→ 复盘问题（事件溯源）"全链路。

### Q35：你对这个项目最满意的地方是什么？

**参考回答**：

不是代码量，是设计的可测试性。

三个设计让我特别满意：

1. **状态机形式化**：18 个单元测试 30 秒跑完，覆盖所有合法/非法路径。新增状态不改测试——这是状态机集中管理的红利。

2. **ScoringEngine 接口化**：换评分策略不改调度主逻辑。DynamicScoring 加上去时，调度代码一行没改，只是改了注入配置。

3. **事件溯源**：出问题时一条 SQL 回溯全流程。不是靠翻日志，是靠结构化数据查询。

这三个设计的共同点：**把复杂度集中到一处，让其他地方变简单**。状态机集中了流转规则、接口集中了策略切换、事件表集中了审计追踪。这是我认为最有工程价值的设计思路。
