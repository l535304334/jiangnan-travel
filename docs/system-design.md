## 一、三方交互流程

系统涉及三类角色：**乘客、司机、调度中心（系统）**。核心交互如下：

```
乘客                  调度中心（系统）              司机
 │                        │                        │
 │ ① 创建订单              │                        │
 ├────────────────────────►│                        │
 │                        │ ② 估价 + 风控检查        │
 │◄───────────────────────┤                        │
 │                        │                        │
 │ ③ 支付                  │                        │
 ├────────────────────────►│                        │
 │                        │ ④ 触发调度 ★            │
 │                        │  ├ 评分引擎排序所有在线司机 │
 │                        │  ├ 二阶锁防并发冲突       │
 │                        │  └ 分配司机             │
 │◄── WebSocket PUSH ─────┤── WebSocket PUSH ──────►│
 │                        │                        │
 │                        │                        │ ⑤ accept / reject
 │                        │◄───────────────────────┤
 │                        │                        │
 │                        │ ⑥ reject → 自动重派     │
 │                        │  (最多3次, 超限告警)     │
 │                        │                        │
 │                        │                        │ ⑦ 到达 → 开始行程
 │◄── 状态推送 ────────────┤◄───────────────────────┤
 │                        │                        │
 │                        │                        │ ⑧ 完成行程
 │                        │◄───────────────────────┤
 │                        │ ⑨ 自动生成账单           │
 │◄── 账单 ───────────────┤                        │
 │                        │                        │
 │ ⑩ 评价司机              │                        │
 ├────────────────────────►│ ⑪ 更新司机平均评分      │
 │                        ├────────────────────────►│
```

**关键设计决策**：

1. **调度是系统主动触发的**（支付完成后自动进入调度），不是司机抢单模式。这保证了调度策略的一致性——系统可以根据全局状态做最优匹配，而不是让司机凭手速竞争。
2. **拒单后自动重派**而不是退回让乘客等待。用户体验更好，且拒单处罚机制让司机会谨慎拒单。
3. **所有状态变更通过 WebSocket 实时推送**给乘客和司机两端，保持状态同步。

## 二、订单生命周期状态机

### 2.1 完整状态流转图

```
                    ┌──────────┐
                    │ CREATED  │ (0) 乘客创建订单
                    └────┬─────┘
                         │ 支付
                    ┌────▼─────┐
                    │   PAID   │ (7) 支付完成 → 自动触发调度
                    └────┬─────┘
                         │ 派单
                    ┌────▼──────────┐
                    │DRIVER_ASSIGNED│ (9) 系统已分配司机
                    └────┬─────┬────┘
                         │     │
              司机接单 ──┘     └── 司机拒单 → 自动重派(回PAID)
                         │
                    ┌────▼─────┐
                    │ ASSIGNED │ (1) 司机已接单
                    └────┬─────┘
                         │ 司机到达上车点
                    ┌────▼─────┐
                    │ ARRIVED  │ (2) 司机到达
                    └────┬─────┘
                         │ 开始行程
                    ┌────▼────────┐
                    │ IN_PROGRESS │ (3) 行程中
                    └────┬────────┘
                         │ 抵达目的地
                    ┌────▼─────┐
                    │COMPLETED │ (4) 待评价 + 自动生成账单
                    └────┬─────┘
                         │ 评价
                         ▼
                    (司机评分更新)

  取消路径: CREATED/PAID/DRIVER_ASSIGNED/ASSIGNED/ARRIVED → CANCELLED(5)
  退款路径: COMPLETED/CANCELLED → REFUNDED(8)
  风控拦截: CREATED → RISK_BLOCKED(6)
```

### 2.2 为什么用状态机

不使用 if-else 散落在各处的原因：

1. **可审计**：流转规则集中在一张 `Map<OrderStatus, Set<OrderStatus>>` 中，任何人（包括面试官）一眼就能看到所有合法路径
2. **可测试**：18 个单元测试独立验证每一条合法/非法路径，不依赖集成环境
3. **可扩展**：新增一个状态只需要在枚举中加一行 + 流转表中加一个 entry

## 三、调度逻辑设计

### 3.1 调度触发时机

订单支付成功后（状态 = PAID），系统**自动触发**调度流程。不是司机主动抢单——这是平台调度模式，可以基于全局信息做最优匹配。

### 3.2 评分规则

调度系统的核心输出是：**"在当前所有在线空闲司机中，谁最适合这个订单"**。

评分公式（WeightedScoringEngine）：

```
Score = 0.40 × 距离分 (越近越高)
      + 0.30 × 评分分 (avgRating × 20)
      + 0.20 × 空闲分 (空闲越久越高, 上限60min)
      + 0.10 × 拒单惩罚 (每次拒单扣10%, 上限扣100%)
```

在此之上叠加**动态学习层**（DynamicScoringEngine）：

```
finalScore = baseScore + driverModifier

modifier 规则:
  accept → +5  (上限 +20)
  reject → -10 (下限 -30)
  cancel → -3
  衰减: 每10分钟 modifier 向0回归50%
```

### 3.3 并发控制

这是调度系统最核心的工程问题。

**场景**：订单 A 和订单 B 同时计算出"司机 3 是最优选择"。

**方案**：二阶分布式锁（基于 Redis Redisson）

```
Phase 1: lock "order:dispatch:{orderId}"    ← 确保同一订单不被重复派
Phase 2: tryLock "driver:lock:{driverId}"   ← 500ms 超时
         ├ 成功 → 分配
         └ 超时 → 司机已被其他订单锁定 → 尝试下一位候选
```

**安全保证**：
- 锁顺序 100% 统一（order → driver）→ 无死锁
- tryLock 不阻塞 → 无活锁
- 加锁后重读 DB → 防 ABA 竞态
- 所有候选失败 → 记录 ORDER_ASSIGN_FAILED → 告警

### 3.4 派单失败处理

- 司机拒单：自动重新派单（最多 3 次）。司机扣分 -10
- 超最大尝试次数：记录失败事件 + 抛出异常 → 人工介入
- 无可用司机：记录失败事件 + 提示"稍后重试"

## 四、权限控制模型

系统采用 **RBAC（基于角色的访问控制）**，通过 Spring Security + JWT 实现。

| 角色 | 权限范围 |
|------|---------|
| **乘客 (USER)** | 创建订单、支付、查看/取消自己的订单、评价司机、管理地址 |
| **司机 (DRIVER)** | 查看待接订单、接单/拒单、更新位置、查看收入统计 |
| **管理员 (ADMIN)** | 用户管理、司机审核、订单管理、风控告警处理、数据大屏、系统配置 |

**实现方式**：
- JWT Token 中包含角色信息（`role` claim）
- 前端路由守卫 + 后端 `@PreAuthorize` 注解双保险
- 乘客只能操作自己的订单（`userId` 校验）
- 司机只能操作指派给自己的订单（`driverId` 校验）

## 五、系统扩展性设计

### 5.1 当前可低成本扩展

| 扩展方向 | 改动量 | 方式 |
|---------|--------|------|
| 新增订单状态 | 1 文件 1 行 | 枚举 + 流转表追加 |
| 替换评分策略 | 1 文件 1 行 | 实现 ScoringEngine 接口，改注入 |
| 新增事件类型 | 1 行调用 | recordEvent() 加参数 |
| 接入真实支付 | 1 文件 | PaymentServiceImpl 替换模拟逻辑 |

### 5.2 未来可扩展方向

| 方向 | 方案 |
|------|------|
| 多城市分区调度 | Redis Sorted Set 维护城市级司机池，findCandidates 只查当前城市 |
| 实时司机排名 | 用 Redis Sorted Set 替代 DB 全表扫描 → O(log N) 查询 |
| 事件异步化 | order_event 接入 Kafka → 下游异步处理（统计、告警、数据仓库） |
| 评分引擎升级 | 接入 ML 模型（只需实现 ScoringEngine 接口，零改动现有代码） |
| 水平扩展 | Spring Boot 无状态 → 加实例 + Nginx 即可；瓶颈在 MySQL 写 + Redis 单点 |
| 分库分表 | 按城市/时间段分片 t_order + t_order_event |

### 5.3 设计原则

1. **接口隔离**：ScoringEngine 是接口，不是具体实现。策略可插拔
2. **事件驱动**：状态变更通过事件记录，未来可异步消费
3. **无循环依赖**：所有 Service 依赖方向统一（上层 → 下层）
4. **状态机显式化**：不散落 if-else，新增状态可预测
