## 一、项目描述重写

### 1.1 一句话简介

> 从零设计并实现了一个**基于分布式锁和自适应评分引擎的并发出行调度系统**，解决了多订单并发派单场景下的**分配一致性、调度公平性和系统收敛性**三个核心工程问题。

### 1.2 项目背景

网约车调度系统的核心挑战不在于"把订单派给司机"，而在于**"在 50 个订单和 20 个司机同时竞争时，如何保证正确性、公平性和稳定性"**。这三个问题在单机环境下可以用一把 `synchronized` 解决；但在分布式环境下，需要跨越 JVM、跨越请求的互斥机制——而且这种机制必须**不会死锁、不会饥饿、不会因为某个司机的异常行为导致整个系统不稳定**。

本项目从真实出行场景出发，模拟了从乘客下单、支付、调度、司机接单、行程执行、完成评价到账单生成的完整业务闭环，并重点在调度层做了工程化深度设计。

### 1.3 核心工程问题

| 问题 | 现象 | 我的方案 |
|------|------|---------|
| **分配一致性** | 一个司机被两个订单同时分配 | 二阶分布式锁（order lock → driver tryLock） |
| **调度公平性** | 好司机永远拿订单，差司机永远拿不到 | 可收敛的评分引擎（拒单惩罚 + 时间衰减 + 空闲优先） |
| **系统收敛性** | 评分差异越来越大，系统不稳定 | 10 分钟半衰期衰减 + modifier 上下限 |
| **状态可追溯** | 出问题后无法复盘 | 事件溯源设计（order_event 记录所有状态变更） |
| **可观测性** | 系统是黑盒，不知道是否正常 | 三层监控（Metrics + Health + Anomaly） |

## 二、技术亮点重构

> 以下每个技术点都按"工程问题 → 设计决策 → 量化结果"结构表达。

### 亮点 1：复杂订单生命周期一致性管理

**问题**：出行订单有 10 个状态、15+ 条合法流转路径。散落的 `if-else` 会导致流转规则不可见、不可测试、不可维护。

**设计**：将状态机**形式化为枚举 + 流转表**。所有合法路径集中在一张 `Map<OrderStatus, Set<OrderStatus>>` 中，每个业务方法通过 `guardTransition()` 一行代码防御非法流转。

**结果**：18 个单元测试覆盖全部合法/非法路径；新增状态只改 1 个枚举文件；新增流转路径只加 1 行配置。

### 亮点 2：高并发派单一致性保障机制

**问题**：多个订单同时竞争同一个司机时，如何保证一个司机不被重复分配？单机 `synchronized` 无法跨 JVM/跨请求工作。

**设计**：**二阶分布式锁（Two-Phase Locking）**。

- Phase 1：订单锁 `order:dispatch:{id}` — 保证同一订单不被重复派
- Phase 2：司机锁 `driver:lock:{id}` — tryLock 500ms 超时，失败自动 fallback 到下一位候选
- 安全保证：锁顺序 100% 统一 → 数学上无死锁；加锁后重读 DB → 防止 ABA 竞态

**结果**：**100 订单 × 20 司机并发压测，零重复分配、零订单丢失、零死锁。**

### 亮点 3：可收敛的动态调度策略系统

**问题**：静态评分（距离 × 权重）会产生正反馈循环——排名高的司机永远拿订单，其他司机永远拿不到。

**设计**：在静态加权评分之上叠加**动态学习层**：

```
baseScore(距离40%+评分30%+空闲20%+拒单惩罚10%) + driverModifier(反馈±衰减)
```

反馈规则：接单 +5 分，拒单 -10 分，取消 -3 分；10 分钟半衰期自动向 0 回归；上下限 (-30, +20)。

**结果**：**5 轮派单后成功率从 ~50% 提升至 ~70%，评分 modifier 波动从 ±30 收敛到 ±15 以内。**

### 亮点 4：事件溯源式审计追踪系统

**问题**：订单从创建到完成经历 8 个状态变更，出问题后如何在 30 秒内定位根因？

**设计**：所有状态变更以事件形式写入 `order_event` 表，覆盖 12 种事件类型。不是操作日志——是**轻量级事件溯源**。

**结果**：一条 SQL 即可回溯任意订单的完整生命周期；统计"系统派单 vs 司机手动接单"比例无需联表查询。

### 亮点 5：三层可观测性体系

**问题**：仅靠"看日志"无法判断系统健康状态。

**设计**：构建了数据层（Metrics）、评分层（Health）、检测层（Anomaly）三层体系：

- **Metrics** — 回答"发生了什么"：成功率、平均延迟、司机负载分布
- **Health** — 回答"系统是否健康"：加权公式综合评分（S/A/B/C/D）
- **Anomaly** — 回答"是否有异常"：连续拒单检测、锁竞争热点、评分波动告警

**结果**：调度异常可在指标刷新后直接定位到具体司机或具体锁 key。

### 亮点 6：分布式环境下的状态一致性设计

**问题**：订单状态、司机状态、支付状态分布在三个独立的领域模型中，任何一处的不一致都会导致业务错误。

**设计**：三个独立的状态机（OrderStatus / DriverStatus / PaymentStatus）通过**业务方法中的 guard 校验**和**Redis 分布式锁的串行化**保证状态一致性。状态变更必定伴随 order_event 记录——不记录事件就不能改状态。

## 三、系统架构表达优化

### 3.1 四层架构

```
┌────────────────────────────────────────────┐
│  业务层 (Business Layer)                    │
│  订单生命周期 | 支付流程 | 账单生成 | 评价系统  │
│  职责：业务规则执行 + 状态机流转              │
└────────────────────┬───────────────────────┘
                     │
┌────────────────────▼───────────────────────┐
│  调度层 (Dispatch Layer) ★核心               │
│  司机筛选 | 评分排序 | 分布式锁 | 派单/重派    │
│  职责：并发安全 + 资源公平分配               │
└────────────────────┬───────────────────────┘
                     │
┌────────────────────▼───────────────────────┐
│  学习层 (Learning Layer)                    │
│  静态评分(距离+评分+空闲) | 动态反馈(±衰减)     │
│  职责：策略可插拔 + 系统自收敛               │
└────────────────────┬───────────────────────┘
                     │
┌────────────────────▼───────────────────────┐
│  观测层 (Observability Layer)               │
│  DispatchMetrics | SystemHealth | Anomaly   │
│  职责：数据采集 + 健康评分 + 异常检测         │
└────────────────────────────────────────────┘
```

### 3.2 核心链路（订单流转全过程）

```
乘客下单 → 支付 → 系统派单(二阶锁) → 司机接单/拒单(动态评分)
→ 到达 → 行程开始 → 行程完成 → 自动生成账单 → 乘客评价
→ 所有节点记录 order_event
```

**关键设计点**：
- 支付后订单进入 PAID 状态即**自动触发调度**
- 司机拒单 → 评分扣分 → **自动重新派单**（最多 3 次，超限告警）
- 订单完成后**自动生成账单**（距离费 + 时长费 + 高峰加价 - 优惠券）
- 评价后**同步更新司机平均评分**（DB 聚合，非应用层计算）

### 3.3 并发模型（如何避免重复派单）

```
订单A ──→ lock(order:dispatch:A) ──→ 选司机3 ──→ tryLock(driver:lock:3) ──→ 成功 → 分配
订单B ──→ lock(order:dispatch:B) ──→ 选司机3 ──→ tryLock(driver:lock:3) ──→ 超时 → fallback 司机7

保障:
  1. 锁顺序100%统一 (order → driver) → 无循环等待 → 无死锁
  2. tryLock 500ms 超时 → 不无限等待 → 无活锁
  3. 获取锁后重读 DB → 防止 ABA 竞态
  4. 所有候选失败 → 记录 ORDER_ASSIGN_FAILED → 明确告知调用方
```

## 四、量化成果

### 4.1 性能指标

| 指标 | 数值 | 说明 |
|------|------|------|
| 单订单调度延迟 | < 150ms | 含锁获取+评分计算+DB更新 |
| 50 订单批量派单 95pct 延迟 | < 350ms | 含锁竞争+fallback |
| 100 订单 × 20 司机吞吐 | 100% 订单进入调度队列 | 0 丢失 |
| 单元测试覆盖 | 18 个用例, 100% 通过 | 覆盖全部合法/非法状态流转 |

### 4.2 收敛效果

| 轮次 | 派单成功率 | 评分波动（max\|modifier\|） | 拒单率 |
|------|-----------|---------------------------|--------|
| 第 1 轮 | ~50% | ±30 | ~15% |
| 第 3 轮 | ~65% | ±20 | ~10% |
| 第 5 轮 | ~70% | ±15 | ~8% |

**趋势**：成功率 ↑ 20pp，拒单率 ↓ 7pp，评分波动 ↓ 50%。系统在 5 轮内收敛到稳定状态。

### 4.3 稳定性结果

| 指标 | 结果 |
|------|------|
| 重复分配司机 | 0 次（100 订单验证） |
| 订单丢失 | 0 次 |

> **江南出行智慧调度系统** | 后端架构与核心调度设计
>
> 从零设计并实现了一个并发出行调度系统（Spring Boot + Redis Redisson + MySQL）。核心解决了多订单并发派单场景下的**分配一致性和调度公平性**问题：通过二阶分布式锁（order lock → driver tryLock + fallback）保证零重复分配；通过**可收敛的动态评分引擎**（加权评分 + 反馈学习 + 时间衰减）实现调度自稳定。压测验证 100 订单 × 20 司机场景下零死锁、零丢失、成功率收敛至 70%+。完整实现了订单状态机、事件溯源审计、三层可观测性体系。

### 5.2 面试 30 秒介绍

> "我设计了一个出行调度系统。核心解决一个问题：多乘客同时下单、多司机同时竞争时，怎么保证**一个司机不会被分配给两个人**、**一个订单不会被两个司机接走**。
>
> 我的方案是**二阶分布式锁**——先锁订单，再 tryLock 司机，失败自动 fallback。加了一个**自适应评分引擎**——距离近、评分高、空闲久的优先，但拒单多的司机会被自动惩罚、排名下降。100 订单压测，零重复分配、零死锁。"

### 5.3 面试 2 分钟介绍

> "我做的是一个网约车调度系统。技术栈 Spring Boot + Redis + MySQL。
>
> **核心挑战是并发调度**——50 个乘客同时下单、20 个司机在线，你要在几百毫秒内完成匹配，而且不能出现重复分配。这在滴滴/Uber 是真实的生产事故场景。
>
> **我的方案有两层**。第一层是并发控制：二阶分布式锁。先锁订单保证不重复派，再 tryLock 司机——500 毫秒超时，谁先拿到谁得，拿不到的自动 fallback 下一位候选人。锁顺序 100% 统一，数学上无死锁。第二层是调度策略：做了一个可插拔的评分引擎——距离 40%、评分 30%、空闲 20%、拒单惩罚 10%。关键是上面加了动态学习层：接单加分、拒单扣分、10 分钟衰减。这样系统会**自然收敛**——拒单多的司机排名下降，空闲久的司机被推上来。
>
> **第三个设计是事件溯源**——所有状态变更都记录在 order_event 表里，这不是日志，是轻量 CQRS。出问题时一条 SQL 回溯全生命周期。
>
> 最后做了可观测性：Metrics 告诉你"成功率 65%"，Health 告诉你"等级 C 需要关注"，Anomaly 告诉你"Driver #5 连续拒单 7 次可能异常"。
>
> 压测 100 订单 × 20 司机，零重复分配、零丢失。核心调度逻辑不到 300 行。"

## 六、面试追问预期与应答要点

| 面试官可能追问 | 应答方向 |
|-------------|---------|
| "为什么不用乐观锁？" | 出行场景司机资源稀缺，碰撞率必然高，乐观锁重试成本大。悲观锁（tryLock）在碰撞率高时更合适 |
| "锁超时为什么是 500ms？" | 权衡值——太短导致高碰撞率下大量失败，太长导致请求排队。经验值，实际需要根据司机池大小调参 |
| "有没有更简单的方案？" | 单机可以用 synchronized。分片方案（按城市分区）可以降低竞争。但通用性不如二阶锁 |
| "DynamicScoring 存在内存里，重启丢了怎么办？" | 当前 demo 级别设计。生产环境可以持久化到 Redis 或定期快照到 DB |
| "如果有 10000 个司机怎么办？" | findCandidates 全量扫描会成瓶颈。方案：Redis Sorted Set 实时维护在线司机排名，O(log N) 查询 |
| "怎么测试并发正确性的？" | 压测后验证 driverId 唯一性集合 + 状态分布完整性。不是"看起来正常"，是数学证明无重复 |
| "这个系统最大的 bug 是什么？" | 早期版本在加锁后没有重读 DB，导致 ABA 问题——一个请求拿到锁后读到的是过期状态。修复后加入了重读逻辑 |
