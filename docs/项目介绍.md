## 一、3 分钟项目介绍稿

> 可直接用于面试开场。括号内为提示，面试时不读。

各位面试官好。我介绍的是我独立设计开发的一个网约车调度系统——**江南出行**。

这个项目的核心是一个问题：**多乘客同时下单、多司机在线时，怎么保证派单不出错**——不会一个司机被分给两个人，也不会一个订单没人接。

我做了三个关键设计。

**第一，状态机**。订单从创建、支付、派单、接单、行程、完成，总共 10 个状态。我没有用 if-else 散落在各处，而是把所有合法流转写在一张表里。任何一个状态变更都先检查是否合法。18 个单元测试覆盖了所有合法和非法的路径——新增状态只改一个文件。

**第二，并发调度**。这是最难的部分。50 个订单同时抢 20 个司机，怎么保证不重复？我用 Redis 实现了二阶分布式锁——先锁订单防重复派，再 tryLock 司机防重复分配。拿不到锁的自动 fallback 下一位候选人。锁顺序 100% 统一，数学上保证无死锁。压测 100 订单、20 司机，零重复分配、零丢失。

**第三，评分收敛**。如果永远把订单给评分最高的司机，其他人永远拿不到——这叫正反馈循环。我加了一个动态学习层：拒单扣分、接单加分、10 分钟衰减回到正常。5 轮派单后成功率从 50% 升到 70%，系统自己收敛。

整个系统全栈实现——Spring Boot 后端、Vue 3 前端、MySQL + Redis。事件溯源记录所有状态变更，外加三层可观测性。核心调度逻辑不到 300 行，但涵盖了几个我认为很重要的分布式系统设计点。

谢谢。

## 二、项目背景

### 2.1 业务背景

江南出行是一个面向江西省内的网约车智慧出行平台，覆盖乘客端、司机端、管理后台三端用户。产品定位为"行遍江西，智享出行"，融合江西文旅元素，支持市内短途（≤50km 即时出行）与城际长途（>50km 跨城出行）双引擎场景。

### 2.2 工程挑战

网约车调度系统的核心挑战不在于"把订单派给司机"，而在于**"在 50 个订单和 20 个司机同时竞争时，如何保证正确性、公平性和稳定性"**。这三个问题在单机环境下可以用一把 `synchronized` 解决；但在分布式环境下，需要跨越 JVM、跨越请求的互斥机制——而且这种机制必须不会死锁、不会饥饿、不会因为某个司机的异常行为导致整个系统不稳定。

### 2.3 五个核心工程问题

| 问题 | 现象 | 我的方案 |
|------|------|---------|
| **分配一致性** | 一个司机被两个订单同时分配 | 二阶分布式锁（order lock → driver tryLock） |
| **调度公平性** | 好司机永远拿订单，差司机永远拿不到 | 可收敛的评分引擎（拒单惩罚 + 时间衰减 + 空闲优先） |
| **系统收敛性** | 评分差异越来越大，系统不稳定 | 10 分钟半衰期衰减 + modifier 上下限 |
| **状态可追溯** | 出问题后无法复盘 | 事件溯源设计（order_event 记录所有状态变更） |
| **可观测性** | 系统是黑盒，不知道是否正常 | 三层监控（Metrics + Health + Anomaly） |

- 暴力破解防护：5 次失败锁定 15 分钟
- WebSocket 连接限流：AtomicInteger 全局计数（1000/500/1000）
- 计价防篡改：后端根据实际距离校验 tripType

### 4.4 前端三端实现

- 三端路由守卫（乘客/司机/管理员）
- WebSocket 实时推送（司机位置 + 订单状态 + 通知）
- 高德地图组件（江西地标坐标库 + Haversine 距离计算）

### 4.5 可观测性体系

- Metrics：成功率、平均延迟、司机负载分布
- Health：综合健康评分（S/A/B/C/D 五级）

## 五、核心难点

### 难点 1：并发调度的分配一致性

**场景**：50 个订单同时竞争 20 个司机，必须在几百毫秒内完成匹配，且不能出现重复分配。

**挑战**：这在分布式环境下不是一把 `synchronized` 能解决的。多个请求跨 JVM、跨请求竞争同一个司机资源，必须保证：
1. 一个司机不被两个订单同时分配
2. 一个订单不被两次派单
3. 不死锁、不活锁

### 难点 2：调度公平性的数学保证

**场景**：如果永远把订单给评分最高的司机，好司机永远拿订单，差司机永远拿不到——正反馈循环。

**挑战**：需要一种机制让系统"自己收敛"——拒单多的司机排名下降，空闲久的司机被推上来，但不能震荡。

### 难点 3：状态一致性的跨域保证

**场景**：订单状态、司机状态、支付状态分布在三个独立的领域模型中，任何一处的不一致都会导致业务错误。

**挑战**：如何保证三个状态机协同流转？如何保证出问题后能快速复盘？

### 难点 4：ABA 竞态问题

**场景**：线程 A 读取司机状态为"空闲"，线程 B 在此期间将其改为"忙碌"，线程 A 拿到锁后仍认为"空闲"——ABA 问题。

**挑战**：加锁后必须重读 DB，防止基于过期状态做决策。这是在压测中真实遇到的问题。

## 六、技术方案

### 6.1 二阶分布式锁（Two-Phase Locking）

```
Phase 1: Lock order → key = "order:dispatch:{orderId}"
         保证同一个订单不会被派两次

Phase 2: tryLock driver → key = "driver:lock:{driverId}"  (timeout=500ms)
         保证同一个司机不会被两个订单同时锁定
         如果tryLock失败 → skip → 尝试下一位候选

安全保障:
  1. 锁顺序100%统一 (order → driver) → 无循环等待 → 无死锁
  2. tryLock 500ms 超时 → 不无限等待 → 无活锁
  3. 加锁后重读 DB → 防止 ABA 竞态
  4. 所有候选失败 → 记录 ORDER_ASSIGN_FAILED → 明确告知调用方
```

**压测结果**：100 订单 × 20 司机，零重复分配、零丢失、零死锁。

### 6.2 可收敛的动态评分引擎

```
最终评分 = 静态评分 + 动态 modifier

静态评分 = 距离 × 40% + 司机评分 × 30% + 空闲时间 × 20% + 拒单惩罚 × 10%
动态 modifier:
  - 接单: +5 分
  - 拒单: -10 分
  - 取消: -3 分
  - 10 分钟半衰期自动向 0 回归
  - 上下限: (-30, +20)  防止极端值
```

**收敛效果**：5 轮派单后成功率从 ~50% 提升至 ~70%，评分 modifier 波动从 ±30 收敛到 ±15 以内。

### 6.3 事件溯源式审计追踪

所有状态变更以事件形式写入 `order_event` 表，覆盖 12 种事件类型：
- DRIVER_ASSIGNED / DRIVER_REJECTED / ORDER_REASSIGNED
- TRIP_STARTED / TRIP_COMPLETED / ORDER_REVIEWED
- ORDER_ASSIGN_FAILED / DRIVER_RELEASED 等

一条 SQL 回溯任意订单的完整生命周期，为统计分析和未来 CQRS 架构打基础。

### 6.4 形式化状态机

```java
public enum OrderStatus {
    CREATED, PAID, DRIVER_ASSIGNED, ASSIGNED, DRIVER_ARRIVED,
    TRIP_STARTED, COMPLETED, PAID_FINAL, REVIEWED, CANCELLED;

    ALLOWED_TRANSITIONS = Map.of(
        PAID,            Set.of(CREATED),
        DRIVER_ASSIGNED, Set.of(PAID),
        ASSIGNED,        Set.of(PAID, DRIVER_ASSIGNED),
        // ... 15 条合法路径
    );

    public boolean canTransitionFrom(OrderStatus from) {
        return ALLOWED_TRANSITIONS.get(this).contains(from);
    }
}
```

18 个单元测试覆盖全部合法/非法路径。新增状态只改 1 个枚举文件。

| 层 | 回答的问题 | 实现 |
|----|-----------|------|
| Metrics | "发生了什么" | 成功率、平均延迟、司机负载分布 |

## 七、项目收获

### 7.1 技术上的收获

真正理解了分布式锁的语义。不是"用了 Redisson"就完了——锁顺序为什么重要、tryLock 和 lock 的区别、ABA 问题怎么发生怎么防、死锁的必要条件——这些东西看书和实际写代码是完全不同的体验。

### 7.2 工程上的收获

学会了"先设计再编码"。状态机的形式化、事件的溯源设计、评分的收敛分析——这些都不是写代码写出来的，是坐下来画图、列表、算复杂度得出的。如果一上来就写代码，大概率会写成 if-else 地狱。

### 7.3 方法上的收获

验证了 AI 辅助开发的正确姿势。不是让 AI 替你做决定，是让 AI 帮你做执行层的工作——你负责判断和决策，AI 负责生成代码、写测试、做 code review。这个分工很关键。而且建立规则约束 AI 的行为，比每次口头纠正高效得多。

### 7.4 量化成果

| 指标 | 数值 |
|------|------|
| 单订单调度延迟 | < 150ms |
| 100 订单 × 20 司机吞吐 | 100% 订单进入调度队列，0 丢失 |
| 调度收敛 | 5 轮内成功率从 50% → 70% |
| 重复分配 | 0 次（100 订单验证） |
| 死锁 | 0 次（二阶锁顺序统一保证） |
| 测试覆盖 | 81 个后端测试 + 155 个前端测试，100% 通过 |
